# Speed cases

These BPL programs supply the native and browser speed tests. Each file owns one shared setup. `arrays.bpl` compares ordinary, exact and 32-bit arithmetic; the other files cover images, model objectives and derivatives, call overhead, structure, mapped functions and tables. `growth.bpl` and `steps.bpl` hold count-only cases: functions whose costs must grow linearly and allocate what their results need, and calls of dfns and steps of operators. The [record format](../reference/README.md#timed-cases) also supports independent result checks.

A footer gives three time budgets: macOS on Apple silicon, Linux on x86, and wasm under Node, or `-` for none. Count fields follow, such as `instructions macos 20.2 linux 33.1` and `allocated linux 8`. Native matrix products and decompositions use Accelerate on macOS and Rustymath's own kernels on Linux. `rustymath_timing::NATIVE_COLUMN` picks the native column. Machines with none, such as Linux on Arm, report each cost with `budget -`. Each speed test, native or browser, fails on a budget or a count only on the CPU that the budgets were set for, `rustymath_timing::BUDGET_CPU`: Jeremy's Mac for macOS, and Syd1 for Linux and wasm. On any other CPU, it reports every cost and marks each case still over its budget.

A copy is one read and one write of `n` 64-bit floats. Costs normalize to the machine's stored copy time, or one measured once. The `widths` section instead compares 32-bit time with the same expression in `exact`. A `static` section repeats its file's workloads with 32-bit integers and floats, still counting 64-bit copies: each float pass moves half the bytes and has twice as many vector lanes. Its expected cost is normally half the 64-bit cost. `images.bpl` is the one file whose data passes the last cache: 72 MB arrays, on which costs in copies don't depend on size.

A copy budget is the expected cost times the multiplier that `set_budgets` applies, at least 0.5, as basedpl's DEV.md gives. A footer holds that rule budget, and a `⍝⍝⍝ held` or `⍝⍝⍝ busy` line among a case's directives raises one of its columns to the budget for the cost it gives, as DEV.md describes. A width-ratio budget adds 0.25 to the expected fraction. A later expected cost needs a fuller understanding, not just a slower measurement. Preserve the comments recording each expected cost and later changes. One expected cost serves every platform until a specific platform difference is found.

A count is a measurement: the instructions and the bytes allocated for each of the setup's `n` items, with compiling off, in a warmed run, or for each step in a `steps` section. Counts don't vary with load, so they show a lost inline or an extra pass or copy that timings hide. A count fails above 1.25 times its value, or 1.1 times in the `calls` and `steps` sections, and allocated bytes get one byte an item more. After a change that moves counts, set them again with `set_counts(log)` from a `BASEDPL_COSTS` log.

On CI, wasm's 128-bit SIMD and lack of fused multiply-adds make vector arithmetic cost about twice its native AVX2 cost. Such wasm budgets are twice that expected cost. Scalar and memory-bound work has a smaller difference. CI's x86 runner is an AMD Ryzen 9 7950X3D. On macOS, Rustymath's `tests/speed.txt` header records Accelerate's matrix-product rates in flops per copy time; a case far from its class's rate records its own measurement.

`BASEDPL_COSTS=1 cargo nextest run --cargo-profile release --test speed --no-capture` logs all native costs and counts. `bpl-tests speed_costs` measures the same sources through a worker. `node --no-liftoff --test tests/wasm-speed.mjs` measures them in a browser build. `set_budgets(expected, path='tests/speed/arrays.bpl')` updates only the selected footers, and `set_counts(log)` the counts.
