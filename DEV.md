# Development

Language: concise to write, simple to read, consistent. A design rule is a plan on trial: discuss it when applying it makes a useful expression harder to read, removes something expressible or adds a special case; APL familiarity and compatibility aren't costs there. API change: change callers; no compatibility layers. Each kind of thing takes the general path: a system name resolves to a function, compiles as a glyph does.

Speed and simplicity before edge cases no real user meets. Follow IEEE, Rust and CPU behaviour where reasonable. Precision: rustymath `DEV.md`'s "Overview".

A form with a reasonable meaning gives a result, not an error; a silent result that is a bug in some programs is fine if it buys useful behaviour or speed. Settled: negative positions count from the end in every selection (Python), though `x.[i-1]` at `i=0` then reads the last item. `⌈` beside NaN: NaN or the other argument, whichever its kernel gives.

Dynamic kinds (default): the APL REPL experience most users want most of the time: machine integers that widen within machine widths and wrap at i64, explicit unbounded `ᵣ` integers/rationals, tolerant comparison. Static kinds: speed-sensitive work. Supporting both costs complexity, not static speed. Large work runs in notebook cells and scripts, not the REPL.

Typed programs and the JIT must end in fairly simple, very fast code; otherwise the approach is in question. Static kinds: integer programs should fuse, compile and run array-wise, by the simplest implementation that allows → one integer regime: ordinary integer = fixed integer of `int` width; overflow should wrap on every route (per-item checks and error paths out of fused or compiled loops cost speed and code); every integer operation should compute at its type's width. Each width's kernels cost compile time, binary size, code: add a kernel family only where its benefit outweighs that.

Big-data analysis runs keyed arrays of functions over keyed arrays of data → keyed and named arrays should fuse and compile as plain ones do; missing-item and fill semantics can change to make that fast and reasonably simple.

Not worth optimizing: laziness between cells; chains that rebind a name so earlier lines compute nothing. Pending arrays fuse large calls in code no trace holds. A view (window, transpose) stays a view until a call needs its items in memory.

Bare number = float (`3`; integer `3ₓ`): a language rule, not an implementation one; an internal route may run a whole float as an integer where the result can't change.

Accuracy: `nbs/numbers.qmd`'s "Accuracy": floats within 4 ulps of correctly rounded, except those rustymath's accuracy page lists; some results exact. Unpromised: last bits, behaviour of infinities and NaNs, zero's sign, and which value a write keeps at a repeated position. Last bits can differ by thread count, array size, platform, build, run, route and spelling (each can reorder a fold such as `+/`). FMA and reassociation can overflow differently near the range limits. A few ulps traded for real speed or simpler code become an exception documented on rustymath's accuracy page. Agents chasing identical bits or tighter-than-documented bounds have cost many rewrites. Never spend speed, memory or code on agreement between results, reproducibility, or accuracy past documented bounds, unless Jeremy agrees a real, common use needs it:

- Don't make a fused, compiled or batched route copy another's fold order, block structure or kernel to match its bits; each route may regroup folds for speed.
- Don't add reference cases, harness runs or tests comparing floats bit for bit across routes, thread counts or array sizes, or checking behaviour of infinities and NaNs or zero's sign; compare within the Numbers page's accuracy.
- Don't count identical bits as a design benefit, or differing last bits as a regression.

Non-commitments don't license breakage: keep the exact results the Numbers page lists. Remove code existing only for agreement between results or accuracy past documented bounds, where removal cuts lines or adds speed without substantive complexity and breaks nothing else.

Costs in copies: `BASEDPL_COSTS=1 cargo test --test speed`, `basedpl.bpltests.time_cases(cases)`, or `time_cases(cases, section='models.bpl:static')` with a speed file's setup and a section's preferences. A copy: time to write the data's item count of negated floats to a second buffer.

- `rustymath::timing::COPIES`: stored copy times per speed-test machine, by CPU, item size and item count; the slow end of normal; for copies whose source plus destination fit in cache, 64 MiB (`CACHED_BYTES`). Stored because a 65,536-item copy timed beside each case varied over 3× on CI's runner (source in L3 shared with other VMs) while functions varied at most 1.18×. Larger copies run at memory speed, varying up to 2× between runs on a shared runner, as do those cases: measured once per run. A cached size with no entry: measured once, printing a line to add to `COPIES`. Browser build: own entries (copy under the JavaScript engine); it can't read the CPU name, so `tests/wasm-pkg.mjs` passes Node's.
- Logs: each case's line ends with its time per item (`logged_costs`: per row); one copy line per data size (`copies`).
- Footprint: data plus peak bytes held (`rustymath::memory::peak_held`). Over 1 MiB (`rustymath::timing::CORE_CACHE_BYTES`, one core's L2 on CI's runner), a case also times a copy of its footprint beside it, appending footprint and that copy's time per item to its line (`logged_costs`: `footprints`). Past L2, data reaches L3 and memory shared with other VMs: cases from about 2 MB swung up to 4× between runs, a different few each run; up to 1.5 MB held. Costs still divide by the data's copy; the footprint copy shows whether a case's time follows it.
- Budgets are single-thread. `thread_scaling()` checks threads: a large product, 512×512 SVD and Hermitian eigendecomposition, a stack of QR decompositions, a product of a convolution's windows, a copy of those windows, a large elementwise function, each on 1 and t = min(4, physical cores) threads. Serial fraction s (share of one-thread time that doesn't split) gives expected speedup S = 1/(s + (1 − s)/t) (Amdahl). s: first principles for our kernels; measured for Accelerate on macOS (product, SVD, eigendecomposition, product of windows) and for the copy of windows (memory bandwidth limits copies). The product of windows fails if its rows stop splitting across threads; the copy of windows if a copy's items stop splitting. Failure: below 1 + (S − 1)/2 (2.5 on 4 cores, 1.5 on 2, for full splitting), or below 0.9 for s = 1. Accelerate's SVD and eigendecomposition: s = 1 (GESDD, SYEVD run on one thread whatever its threading setting). Run by the manual `Speed` workflow. Linux counts one core per set of hardware threads sharing a core; a VM not reporting the sets counts each vCPU (the `Speed` workflow's `lscpu` step shows CI's).

Instruction counts: code layout alone moves timings more than a few percent, hiding per-call changes in copies; `instructions(cases)` counts instructions retired, which load and layout don't move. `instructions`, `profile` and `call_profile` run loops as ordinary code (`BASEDPL_LOOPS=ordinary`): counts measure a call's interpretation, which the cases' `⍣N` wrapper would otherwise replay. `replays=True` lets loops replay their recordings, as real runs do: a case that names `N`, such as `{0.5×⍵+⌽⍵-(+/⍵)÷4}⍣N 1 2 3 4`, then counts its loop's replayed steps (22,473 instructions a step, against 26,825 as ordinary code, on 1 November 2026).

- A case is an expression (`k(⌈/⊢)⌸a`) run once per step in `{case ⋄ ⍵}⍣N 0` (that dfn adds about 1,900 a step). A case naming `N` makes its own calls (`{⍵}⍣N 0`: one dfn call a step) and must make one per step: a map like `f¨N⍴0` calls its dfn once on all cells, giving no per-call cost.
- Fresh single-threaded `bpl` processes at four `N`, three each (`runs=`), lowest count per `N`; each successive pair's slope, Δinstructions/ΔN, cancels startup and `setup=`; the median of the three slopes drops a one-off cost starting past some size (`≢•ucs N⍴"ab" "cde"`: about 5×10⁶ more from about 131,350 items). All `N` lie past warm-up, from a rough count at 1,000 steps: allocating cases retire up to about 5×10⁶ extra, varying by process, while the allocator settles; successive `N` 5×10⁸ instructions apart keep that under 1% of a slope. `counts=` sets two or more `N`. Reads `/usr/bin/time -l` (macOS), `perf stat` (Linux).
- `build=` another build; a list (`build=[base, None]`) counts each at the same `N`, side by side, with the first-to-last change.
- A pending result (large windows, a transpose) counts making the pending copy, not the copy (`3↕v`: about 12,000 a step). `force=True` computes each array result with a first item in full, by an indexed write (`3↕v`: about 9 million, the copy, plus about 6,000 for the test selecting those results). Joins compute at once: no `force`.
- `tests/instructions.txt`: instructions per step per case, macOS on Apple silicon. Most cases make one call per step (`{⍵}⍣N 0` to `fib`); three map over the same 64 cells each step via Each, Rank's general path, and a system function's item map. `instruction_budgets()` counts each case through `instructions`: `over` if more than 3% above its count, `stale` if more than 3% below; `tests/test_instructions.py` fails on either, skips other platforms. In the change that makes a call cheaper, lower each count it moves. A new compiler version can move counts by inlining differently: then set them again from `bpl-tests instruction_budgets`. CI checks only speed budgets.
- `profile(case)` (macOS): instructions by function; takes `force=` like `instructions`. A fresh process repeats the case on one thread while `sample` counts each function at the top of the main thread's stack; share × the build's `instructions` count estimates instructions per step, assuming one retirement rate for all functions. `profile_diff(case, base)`: which functions moved a count, from both builds' estimates; a function one build inlines shows under the other only. `base`: a build, e.g. the one installed before a change; `build=`: the build to profile (default installed). Use these before reading machine code.
- `call_profile(case, function)` (macOS, Apple silicon): exact instructions one call of `function` retires, callees included, by function. `lldb` runs the case once per step in a fresh process, lets `skip=` calls pass, single-steps the next to its return. `function`: regex on a demangled name (`binder::derived`), which must have code of its own. `base=`: a build shown beside `build`. Allocator functions and callees share one row (heap-state dependent); a second total excludes it. `profile`'s time-based estimates can misattribute: find the changed function with `profile_diff`, settle it with `call_profile`. Budgets:

- Budget = expected cost × multiplier: 2 under 50 copies, 1.5 for 50-500, 1.3 over 500 (cheap cases vary most). Expected cost: first-principles analysis of what the case should cost; a later one comes from fuller understanding (a platform difference, a missed cost), recorded in the case's comment. The comment above each case or group gives the expected cost and reason, and any platform's own cost and reason. One expected cost serves every platform until a specific platform difference is found (e.g. macOS runs matrix products and decompositions on Accelerate, CI on rustymath's kernels).
- A BPL speed file's `⍝⍝:` footer: rule budgets (expected × multiplier) for macOS on Apple silicon, Linux on CI's x86 runner, then (basedpl only) wasm under Node on CI's x86 runner.
- A case over its rule budget gets a directive holding the column: `⍝⍝⍝ held linux 15.6 wasm 18.9: REASON` (a code gap; each held column with its held cost) or `⍝⍝⍝ busy linux 2.7: REASON` (data past CI's 1 MB L2, which busy hosts slow in some runs). The multiplier applies to the held cost; the case's line shows both (`budget 32 held from 16`). A gap's hold goes stale at 0.9× its rule budget or less (inside the 10% margin a review holds a column at); runs print it `stale`, and its `held` line can go. Busy holds never go stale.
- A case within 10% of its budget on a checking platform gets a dated `held` line raising that column 10% against noise, so CI isn't flaky: held cost = the one whose budget, rounded up as `budget` rounds, is at least 10% higher (`⍝⍝⍝ held wasm 17.6`: 32 → 36); stale by the 0.9× rule.
- A platform cost no run has measured (a Linux or wasm estimate) keeps twice the estimate until CI measures it, marked `~` in held lines (`⍝⍝⍝ held linux ~107: REASON`). Rustymath's tables still sit at twice expected cost (old rule).
- `rustymath::timing`: the multiplier (`budget`); reads (`hold`) and applies (`Budget`) these lines for every speed test. Rustymath's budget files write them as `# held ...`, `# busy ...` above a case's line.
- Over budget: study it, finding a speed bug or something the analysis missed. Avoid raising a budget to match a run without knowing why it costs that.
- Speed tests fail on budgets only on `rustymath::timing::BUDGET_CPU`, the CPU they were set for: the development Mac (macOS), CI's runner (Linux, wasm). Other CPUs print every cost, then cases still over after retries, marked `over`, failing none. Costs in copies depend on CPU caches as well as speed (rustymath's DEV.md: the 9950X in CI's pool).
- `set_budgets(expected)` applies the multiplier and writes rule budgets for `expected`'s cases (dict: case code → expected cost), leaving `held` and `busy` lines. `builds=`: one platform's column; `estimate=True`: twice the cost, for estimates; `sections=`: named sections only (a case can be in several, e.g. `copies`, `widths`); `path=`: a BPL speed file or directory, or rustymath's `tests/speed.txt`, `tests/speed_python.txt`.

Routes:

- `tests/routes.rs`'s `speed_cases_take_their_routes` captures every speed case after warm-up at normal setup and size, forcing results outside timing (`timing::routes`). Plain `cargo test` skips that binary while its cases take minutes; `cargo test --test routes` runs it. `tests/explain.rs`'s `cases_take_their_routes` captures each reference case with route directives once under ordinary preferences, and the coverage matrix. In plain `cargo test`, only it checks route directives; `check_file` checks a file's likewise, on one thread. Route checks decide which calls wait with the Mac's costs on every platform (`fusion::Waits::Reference`, set in `timing::route`), so a directive observed on the Mac holds on CI; real runs and timings use each platform's own costs. `⍝⍝⍝ route NAME` above a case requires that fast route. A permitted slow event never excuses a missing required route.
- Unlisted slow events fail: `stored` (pending items computed outside a fused group), `forced` (a call computing pending items it reads as items; rows with reason `read as values`, an argument such as a count, or `an effect`, the pending arrays that an effect computes first, aren't slow), `fallbacks` (batched fallback), `mixed` (a write leaving mixed storage), `itemwise`, `stopped` (stopped trace). Name them as `•explain` does: function (`forced`), code (`mixed`), route (`itemwise`), reason (the rest). `⍝⍝⍝ allows RECORD "EVENT": principle` permits work (a matrix product reading its arguments whole); `⍝⍝⍝ gap RECORD "EVENT": what should happen` names a fast-path gap. A stopped trace takes `allows` only for a by-design stop (dynamic kinds' value-dependent types), else `gap`. `declined` (a considered route not taken) is informational; a `gap` or `allows` can name its route and reason (`fusion: an exact argument`). Every annotation must match an observed event; remove it when the event disappears. `cargo test -- --nocapture` prints remaining gaps.
- Native selectors (`reference`, `explain`, `routes`, `speed`): `BASEDPL_SOURCE` matches a source name, with or without `.bpl`; `BASEDPL_SECTION` matches a section prefix; `BASEDPL_CASE` matches an ID or code prefix. A selector matching no cases fails. Filtering precedes setup and case execution. The coverage matrix uses source `coverage`. Explain stories use source `explain`, with sections `idioms`, `records`, `read-back`, `accumulation`, `reads`, `declines`, `stops`, `memory`.
- Coverage matrix (`reference::coverage`, in `cases_take_their_routes`; it skips the cases `tests/skipped.txt` lists): scalar numerical objects and defined scalar forms against the executors, on floats, under dynamic and static kinds. Not, Nand and Nor use Boolean inputs in their logical valences. The float cases run: between two other steps of one block stage (`2×*2+x`, `2×(2+x)|y`, `2×(2+x)|c` for c = 0, 1, 2, 0.5, ¯1, `2×c|2+x` for 1, 2); fold `|/2×x`; product `m+.|k`; each one's gradient. Fusion at any size, every stage compiled (`settings::Compiles::Always`). Required routes: mapping `compiled`, fold `fused fold`, gradient `trace`. A block stage running compiled parts takes `compiled`; if its compile setting asks for compiled parts, it declines `compiled` once per step that doesn't lower, named by facts-table form (`compiled: residue`). A call large enough to wait that no block stage computes declines `fusion` with its plan's reason (`fusion::defers`). Missing-route messages list the run's declines.
- `tests/coverage.txt`: accepted gaps, one per line: section, `dynamic`/`static`, tab, case code, tab, a `⍝⍝⍝ gap` (work to do) or `⍝⍝⍝ allows` (known cost) line. Listed cases needn't take their route. Dynamic kinds keep calls whose result type depends on values out of block stages and traces by design; such misses take `allows` lines citing the rule. Lines whose event no longer appears fail (a fix deletes its gap lines), as do lines naming no case. A change opening a gap fails with the case's code and its declines or slow events: add a line naming one, with what should happen. Preparation errors, evaluation errors and panics fail. Canonical metadata excludes forms without a numerical object or a defined scalar body.
- `tests/skipped.txt`: cases a test skips, one per line: test name, tab, section (`*` for every section), tab, case code, tab, the `meta/open.md` item that records why. `reference::skipped` reads it; each run writes the skipped lines to stderr past the test harness's capture, and a line naming no case of its test fails. Remove a line with the fix its item names.
- Events: Rust in both repositories reports routes taken, declines and stopped traces via `rustymath::events`; basedpl records itemwise routes in `•explain`'s rows. Uncaptured reporting costs one atomic load. The route test compares observed successes, declines and fixed itemwise routes with the declared IDs (idiom cases and annotated references included); the inventory includes warm-up, route contracts only the warmed run. It checks event-name coverage, not every branch at an emission site. Study an unexpected event before annotating it, as for a case over budget.

Retries: speed tests and `thread_scaling` retime each failing case after the rest, after each pause in `rustymath::timing::RETRY_PAUSES` (0.1, 1, 10 s; 10 s outlasts longer load bursts from other VMs on CI's runner), failing only cases that fail every time. Before each retry, speed tests and `bpl --costs` keep the thread busy 0.1 s (`rustymath::timing::warm`): idle cores start slow (on this Mac, small cases timed straight after the 10 s pause cost up to 3× without it). Retries print old and new costs (speedups in `thread_scaling`), even in passing runs; `logged_costs` keeps a retried case's lowest. Study a case that needs retries in most runs, as a slowdown.

Before and after: for a change meant to speed something up, or to code every call goes through, time affected cases before and after. Other changes need only the speed test, which fails only past budget, missing smaller slowdowns.

### Codegen and rebuilds

Local `test` builds: incremental, thin LTO across each crate's codegen units (Cargo's default, `lto = false`). Incremental builds put `#[inline]` helpers and generic instances (iterator adapters, `array::map`, `copy_from_slice`) in codegen units of their own, where only LTO can inline them. Thin LTO: per-call instructions 4-18% lower, within about 3% of `dist`; a one-line basedpl edit rebuilds `bpl` in about 9-12 s (6-8 s without LTO); a rustymath edit about 30 s either way. Thin LTO imports a function into another unit, to inline it, only below LLVM's import limit of 100 instructions; a long fused iterator chain can exceed it. What else stays out of line: rustymath's DEV.md "Loops and codegen". Under LTO, rustc runs `.cargo/config.toml`'s extra `passes` before the link step, the loop vectorizer only at that step → configs list `loop-vectorize` before `slp-vectorizer`: listed alone, SLP packed short inner loops' lanes before the loop vectorizer could vectorize them across items (`∪c` 71% slower, `dist` too). After an interrupted build, a link error on undefined `.llvm.<hash>` symbols = stale incremental codegen units: `cargo clean -p <crate> --profile test`.

Moving lines changes the code below them (each panic site, e.g. a bounds check, holds its line) → every unit holding that code recompiles. Split related source into child modules to limit the shifts: e.g. the generic block runner in its own file, `program/blocks.rs` (a one-line edit above a runner in its own file recompiled one 140 KB unit in about 2.4 s; with the runner below it in the same file, about 9 s). Children: `use super::*`; `pub(super)` for parents and siblings. Parents own public re-exports.

Generic loop instances can concentrate in the defining module's codegen unit. A closure passed to a generic adapter such as `map` makes an instance that can compile in another unit → every edit to the closure's function recompiles that unit (once 1.9 MB, about 8 s; a plain loop avoided it). Mark loop helpers, nested ones included, `#[inline]` when their instances must compile with the caller's kernel table. Kernel tables: separate modules `booleans`, `wholes`, `float_kernels`, `complex_kernels`; `at_widths!` gives the concrete widths their own modules. Keep new tables separate; add kernel specializations only for measured gains.

Diagnostics of the current compilation arrangement; don't create scratch builds to approximate it:

- `cargo build --lib --bins --profile test --timings`: the normal build; report under `target/cargo-timings/` separates frontend and codegen time.
- `BASEDPL_UNITS=1 cargo test --test units -- --nocapture`: large units and their functions.
- `BASEDPL_SIZES=pattern cargo test --test units -- --nocapture`: machine code matching a demangled-name regex; basedpl's own codegen units only.
- `BASEDPL_SIZES_DIFF=old:new cargo test --test units machine_code_growth -- --nocapture`: two binaries (e.g. `bpl` before and after a change) compared by generic function, across every crate.

Build on one core for minutes: usually one function an LLVM pass takes minutes over. The loop vectorizer picks each loop's vector width and interleave count from the target's cost model: seconds for arm64 can be minutes for x86-64.

FILE`: passes of 100 s or more, with each function's mangled name. One crate's trace can be gigabytes.

## Parser, evaluator and scopes

The lexer/parser records byte spans and structural syntax without evaluating expressions. `parse` distinguishes complete input, incomplete input and errors. It reads numbers under the current settings, which are process-wide (`settings.rs`). `Session::parse` passes the parser the `hanzi_aliases` setting. `syntax_tree` supplies source tools with structural nodes and recovers invalid chunks as `Error` nodes. `highlight` shares the lexer.

`symbols.rs` owns APL, simplified and traditional Hanzi spellings. Its rows also hold each glyph's names: a glyph name for the character, which is also its page's file name in `nbs/glyphs/`, and a name for each valence, or one name where both valences do the same thing. The glyph reference, named entry and help read them there. Python's exported names read them, with each system function's name, through `symbols::builtins`. `hanzi_aliases` enables Hanzi glyph spellings, canonicalizing token decisions while retaining original source and spans. Other Hanzi remain name characters. `_` quotes the next non-whitespace character into a name, including a glyph alias. The `notation` preference affects structured function/operator display, not stored source, serialization or structural APIs; help and editor metadata use the same spelling table.

The compiler binds a statement right to left by categories (`binder::Compiler`, `Rule::get`, `shifts`). Reductions emit instructions instead of calling functions; shared function nodes are immutable. An array that holds a function as an item has its own category, `Callable` (`Category::bound`). `push` works out each item's role once, as it pushes it: `Category::before` resolves `Callable` against the role of the item below, which is to its right, to `Function` where that item is a subject or an absent `⍺`, and to `Value` otherwise. `Rule::get` and the strengths don't change, and recordings check `Callable` as a category of its own. A function-only operand slot converts such an array to `FunctionNode::Array` in `constant_operand`, and `Function::from_value` makes the same conversion where a call by text needs a function. Primitive/operator rows own names, operand kinds, ranks, pervasion, axis behaviour and reduction identities. Change those rows instead of duplicating metadata in consumers. A non-extending primitive above its natural ranks runs through Rank; pervasive Each/Outer/Rank paths reuse whole-array kernels.

Dot names rewrite to Pick and dot brackets to selection. Numeric subscripts derive selection on arrays and `⍠` on functions from the bound operand. Writable subscripts normalize to selection calls at assignment. `ⱼ`, `ₑ` or `ᵣ` between two arrays then rewrites to the primitives it stands for, as `xⱼy` to `x+y×0ⱼ1` (`syntax::joined_term`). Dot parentheses evaluate a namespace: `T.(expr)` and `T⍎text` bind each key on the first axis of `T` to its item or major cell as a local, resolve other names in the caller and keep assignments local. They share the scoped execution route and lexical lifetime checks. Between functions, dot remains inner product.

`Bindings` (`eval/bindings.rs`) holds every binding: the frames of running calls and scopes, each module's names, the current frame and the running module. Other code reads and writes bindings only through its methods. A lookup gives where a name is bound, as a `Place`, with its binding, and reads, writes and removals take a `Place`. `Bindings::here` gives the place where a plain assignment binds a name. Parsing interns each name as a `Name` (`name.rs`), a number that is the same in every session, and a name becomes text again only where text comes in or goes out. Each frame has slots on one stack that every frame shares: first one for each of the six names that a call binds itself, then one for each of a dfn's locals, the names before an `←` in its statements (`Definition::locals`). A call allocates nothing for its names. A call with no left argument binds `⍺` to an absent argument, so lookup finds the call's own `⍺` and never an outer frame's. A name without a slot, such as one that `⍎` binds or an assignment in a scope binds, goes in its frame's side map. A scope's frame holds its record, and a lookup that the side map misses there reads a key through the record's own index of its keys (`Keys::position`), so a scope copies nothing and a key's text never becomes a `Name`. Each module keeps its names as entries that an index finds, and deleting a name empties its entry without moving the others. A compiled read of a name carries an address (`Bindings::address`): the slots on its lexical chain that can hold it, and its module's entry. It reads through `Bindings::load`, which looks the name up as an uncompiled read does where a frame on the chain binds names without slots or the running module isn't the recorded one. Lexical frames use non-owning parent indices. Closures see live bindings, not snapshots. A dfn's last read of a local, `⍵` or `⍺` takes the binding out of its slot (`syntax::release`), and leaves `Binding::Released`, which stops lookup there with a VALUE error. The binder hands a dfn call the arguments it owns (`Argument`), so `⍵` and `⍺` hold them without a copy. `dispatch` gives a dfn the arguments as its caller gave them, and so a composition or fork with an operand that can use them (`Function::owns`, set when the function is built); it lends them to any other composition or fork, and a compiled statement gives a group's train the arguments that it holds (`operators::train_call`). An operator hands its operand each value that it made and doesn't read again: `∘`'s inner result, a fork's tine results, `⍣`'s states, a fold's running result, and the cells and selections that it gathers. It gives its own arguments to its operand's last call, as `∘`, `⊘`, `↣`, `↢`, a unit `⍚`, `⍣` with one count and a fork's left tine do. It lends them where it reads them after a call, as Under, Rank, Axis, stencils, Over, inner products and `⍣`'s other forms do, and it lends any value that it reads again, such as the state that `⍣∞` compares and the batches that a batched try reruns after a stop. A train reads its arguments in its last part and in each fork's left tine, and the last of those reads takes them. Plain assignment is local; modified/selective assignment updates the nearest existing binding. Retain the resolved place and original array across modifier calls rather than looking the name up again. Returns and outer writes reject functions, including those nested in arrays/prototypes, whose frames would not survive. Tail calls retain dependencies from arguments and the called function. No collector is used; recheck this lifetime reasoning before permitting escaping lexical captures.

Module 0 owns session names. Each `•load` runs in a new module, without the caller's frame and with echo off, and returns its non-private names alphabetically. Modules remain for the session's lifetime. Recursive loading of a canonical path is a DOMAIN error. Paths starting `./` or `../` resolve against the source file; other paths use the working directory. Execute/load do not run the top-level preference header.

Dfns run statements in order and return the last statement's value. Final assignments are silent. An absent left argument propagates through the binder's absent-binding rules; default-left assignment runs only when needed. Guard handlers see bindings as they stood at failure; nothing rolls back. Wildcard `∞::` excludes interrupt, timeout and unsupported errors. Explicit named guards can catch them; catching an interrupt clears its flag.

Every statement compiles before it runs (`eval/tree.rs`). The compiler binds it from its text and the roles of the names it reads, and emits an instruction for each node that needs evaluating and each reduction (`Op`); `Recording::execute` runs them in one loop. `strand`, `attached`, `split_call`, `derived`, `bound_right`, `train` and `tails` in `eval/binder.rs` give the reductions' values, while compiling for constants and while running otherwise. The drop of an absent `⍺` compiles to nothing, and a derive or a bind on constants compiles to a constant, so an operator bound to a constant operand, as in `⍤1`, derives once. A call's result, a field read from it, a subscript's selection and a scope's result bind as values whatever they hold, so no call changes how its statement binds. A value of another category than its instruction compiled with takes the compiled one (`Entity::fit`, `refit`, `returned`). A call or derive result carries `call`: assignments store, and operators other than subscripts and superscripts take, the function its atom holds, and so does a statement's result (`called_as`). Registers hold the compiler's entities (`binder::Entity`), in an inline array of 8 (`INLINE`) or on the heap for a statement that needs more. The recording keeps its constants as entities, and an instruction borrows them, so a call reads a constant's array or function without copying it (`array_of`, `function_of`). Each statement holds two recordings (`Statement::recordings`, `tree::Slots`), so a dfn called with both valences keeps both, and a statement whose facts fit neither compiles and runs uncached. While capture is on, calls, strands, attaches and derived calls carry `Expression`s for dissection (`execute::<CAPTURE>`).

A recording keeps each fact that its binding read: the role at a name's or a dot path's address (`tree::Fact`). A statement checks its facts as it starts (`Recording::holds`), except that a name's first read before anything in the statement acts checks its own role (`Mismatch::Again`, `binder::early`). A role that changed there puts back the bindings that the statement took (`Recording::again`) and raises `ErrorKind::Again`, which only `Session::statement_step` and `Session::bound` catch, to compile the statement again. A read of a name that an assignment earlier in the statement binds takes the assigned category (`Mismatch::Fit`). Any other read whose role changed while the statement ran fails (`role_changed`), after a selective write in the statement or a write inside `⍎`. A call's write that would change the role of a name outside its frame fails at the write (`Session::outer_role`). An unbound name binds as an array (`binder::UNBOUND`). An own-frame slot's role check reads the slot (`Bindings::own_role`), and module entries' facts are checked through an epoch that an entry's role change, any unslotted write, `swap` and `replace` renew (`Bindings::roles`). `∇` and `⍢` record no facts (`Name::fixed`).

Each group or run in the statement is a level, whose instructions sit inline between an `Enter` and an `Exit`. The compiler groups a level's dot reads, subscripts, joiners and runs that start with an operator as it starts the level (`Compiler::members`, `Compiler::joined`), reading their categories through itself, so the groups match how it compiles. Each instruction holds the nodes it reads, so no group outlives the compile. A run that ends in a dyadic operator is a level whose compile starts with the run's right operand on its stack. A group, run or bracket literal that `Session::resolve` evaluates compiles through `Compiler::compile_nested`, which checks that a run reduces to one value (`Compiler::one_value`).

A group or run whose leaves are all literals, primitives, operator glyphs or such groups, and which makes no call, compiles to the array or function it gives, so a train like `(+/÷≢)` builds once. The compiler drops such a group's instructions by truncating back to where the group started (`Compiler::truncate`). A run that ends in a dyadic operator, whose right operand is constant, compiles to a constant too. A group whose last step builds its value as a train exits with the train's tines (`Term::Tines`), and a call of that group calls the tines in place (`Op::CallTines`, `operators::train_call`). The call builds the train and calls it instead while a transformation or `•explain` runs, where two array tines are side by side, and where the rule table marks the train's functions (`operators::calls_tines`, `rules::marks`).

An assignment compiles to one instruction (`Op::Assign`), which runs `Session::assigned`: a store of a plain name straight into the frame's slot that `Bindings::here` found when the statement compiled, or `Session::assign`, the one home of every target form. The compiler finds where a target of more than one node starts (`Compiler::target`), and compiles a modified assignment's function before the instruction, as any function; the instruction reads its register. The instruction holds the target compiled (`tree::Target`, `Compiler::assigned_target`), so running it compiles nothing and reads no name's role: a name, `⎕`, brackets of names, a function's rule, or a selection, whose dot reads and subscripts become selection calls first. A selection compiles into layers (`tree::Layer`). Each splits at a selecting primitive, with its index compiled, for the direct route and the extension of missing keys, and holds the code before its last node, compiled with a seed, for the walk. A run evaluates each index once (`Split::slot`). A default argument, an error guard's kinds and a dfn's last statement compile as other statements do.

Each item of a bracket literal, and each key that isn't constant, is a level whose value goes into the literal at once (`session::listed`). The level that finishes a keyed item makes its entries (`tree::Keyed`), and the `Array` instruction assembles the literal (`tree::assembled`). `resolve` compiles a bracket literal that a dot scope holds, as it compiles a group (`binder::nested`).

Tail calls reuse frames while preserving lexical dependencies. Handlers disable tail reuse. Evaluation depth is capped at 20,000 natively and at 244 in the browser, whose stack runs out first. Each call of a function other than a primitive counts toward it, and so do each statement of a dfn other than its last, each group, each run that ends in a dyadic operator and each bracket item, compiled or not. A compiled statement or level counts with `Session::descend` alone, without the interrupt check and stack growth of `Session::nested`. Calls of primitives other than `⍎` don't count, because a primitive never calls back into BPL. They skip the depth, capture and stack bookkeeping, and on numbers a form that applies a kernel to each pair of items runs that kernel at once (`Primitive::scalar_call`). A separate 20,000-frame limit bounds retained lexical frames. Late-bound name resolution stops at 128 levels. These are execution limits, not a sandbox against arbitrarily deep source, arrays or function graphs.

## Values, layouts and assignment

`Value`: number, character, function, operator or shared array.

- Compact storage: a rustymath `buffer::Buffer` of one dtype (Booleans, narrow integers, width-specific floats or complex numbers, characters); `Items` borrows it as a `buffer::View`. Promotion rules for those dtypes stay in basedpl (`Promotion`, `array/storage.rs`); a rustymath buffer keeps the dtype it's given. Ordinary integer array width (`array::ordinary_width`): narrowest holding its values under dynamic kinds; the `int` width under static kinds, where storage follows kind.
- Mixed storage: `Value`s; memoizes prototype, innermost lexical dependency, whether any item is a function; other properties computed on demand.
- Segmented storage (`Segments`): two or more arrays of one rank and kind, with no keys or names on their axes, held flat as one leaf array, with each item's offset and shape, as DuckDB's list vectors and Arrow's ListView hold lists; an item reads as a view of its range of the leaf, and a view of nested items takes its own first item's prototype (`ArrayData::nested_prototype`). `Value::gathered` builds it with no copy where every item is a view of one stored array (`Segments::of`: Rank's `⊂` cells, a partition's parts, a selection of segmented items). A producer whose items are made together builds its leaf whole (`Segments::new`), as `keyed::text_column` does for `•csv` and `•json` texts, one range for each distinct text. Items computed apart stay mixed. Each's batched try reads items of one layout and kind as one array (`Items::stacked`: a view of a segmented leaf where they lie in order, else a copy). Search, classification and grade compare exact cells, a segmented array's as slices of its leaf, through rustymath's `search::Exact`. A write turns it mixed first (`Storage::values_mut`).
- Layout and storage share one allocation. `Shape` holds ranks 0-2 inline → small arrays allocate no shape. Constructors take `impl Into<Shape>`: pass a slice or an array (`[n]`), not a built `Vec`.
- Shape, key or name change on a shared array → a view of the base's storage, no copy. Part of compact storage (a Rank cell, a partition: `Value::part`) → a view of a range of the base's items; a view keeps its whole base alive (as NumPy's). Part of mixed storage → a copy (the memo covers all items).
- A large result of a fusible float call holds a pending call in place of its storage, computed on first read (`fusion.rs`).
- `Value::view`, `imported_buffer`: the public width-preserving frontend boundary; they give and take rustymath's `View` and `Buffer`, re-exported as `basedpl::buffer`.

Atoms, rank-0 arrays and singleton vectors are distinct. Function nodes hold handles, not lexical frames or Python objects. Functions match by parts; dfns and generators by identity. Operators can be values and cross the native Python boundary. Values and function nodes: `Send + Sync`.

Fill: numeric zero, character blank. Mixed nonempty arrays derive their prototype from the first item on demand; empty arrays need one explicitly. Builders take a value or a lazy prototype function, evaluated only for an empty result. Preserve function handles inside prototypes.

`Layout`: rustymath's `layout::Layout` (dimensions, position keys, axis names) plus the renderer. Methods changing only keys or names keep the renderer (as `select` does); methods building a layout from axes drop it; broadcasting two layouts keeps the renderer they agree on (`Layout::paired`). Rustymath's `agreement` pairs: unites keys, broadcasts through index maps; missing positions read each source's prototype. Equal axis names pair first; remaining axes pair positionally unless both have different names. Result assembly drops colliding axis names; public name attachment rejects duplicates. Contracted axes need equal key sets, keep the first order. Nonempty key lists with no named positions become unkeyed; empty record keys survive.

`Gather` owns copying and widening. `Steps` (rustymath's `gather`): strides, ranges and fills, rotations, offset tables. `Gather::walk` copies compact storage via `rustymath::gather::walk`. Structural operations should use `remap`/gathering, not per-item `Value` reconstruction. Equal-shape cells copy in blocks. `Items` reads counts, positions and axes from compact storage without boxing items. Shape, tally, positions, predicates: dedicated integer and Boolean builders.

Fill choice: `⍠`'s options record or a window specification's `fill` key (`WindowSpec`, `primitive/structural.rs`). `Primitive::fill_for` validates one scalar item of the data's type (`Value::fill_of`); nested data takes any BPL value. Native fills travel with rustymath's mappings through pending copies, kernels and traces. `copied_fill` consumes fills of mixed data eagerly. Keyed pervasive calls attach native fills to their agreements without copying operands first. Values keep the chosen fill; tangents and label ids read their own zero fill. Maps needing two different fills keep separate copies.

Writes: Under with a function, and selective assignment, run the selector on the root while every call builds a node, then walk its result back to the root's positions (`selection::selecting`). A compact root enters as one input node. Any other root enters through leaves (`selection::Leafed`): each compact array or atom, at any depth, as a view of the leaf node for its type of item; each nested array rebuilt from its parts; each host item (exact number, function, operator) copied to an address of its own (`Value::readdressed`).

- The walk follows copies, gathers and joins back to the root (`root_places`). A result that reads the root whole in order → a walk over it (`Targets::Walk`); otherwise offsets, or paths where the root has nested items. A part found by its address, or by its place and shape in its leaf, is taken whole: its write replaces it at any length. A selecting form whose result is its argument itself gives a copy node (`Primitive::call_axis`), which selects every position; a form with `Facts::passes` gives the argument itself, taken whole.
- A root with duals on it walks through each value's primal (`undualed`), and `transform::written` writes each part. A regular batch of the running batched run: the selector runs once, on a batch over its whole (`framed`). Any other batch stops its run. A result that no root node holds → Under uses the selector's inverse; in selective assignment it's a DOMAIN ERROR, as is an element from elsewhere.
- Function-Under applies its selector to a left argument as a plain value; positions-Under passes the left argument whole. Keyed values align to selected keys; nested paths keep empty-cell structure.

Selective assignment removes the binding before writing; `Arc::make_mut` copies only when another holder needs the old array. Repeated targets must read values written by earlier occurrences. `pervasive::scatter` combines each target of `+ - × ÷ ⌈ ⌊` into compact numbers in place, in turn, at the kind the call's plan computes in (`plan::pervasive_on`), via rustymath's `gather::Writes` (`combine`, `try_combine` read a selection's walk a run of offsets at a time, without listing it). Other pervasive modifiers group repeated targets into rounds of distinct positions. A target at a fill reads the fill; its write is dropped. Append updates: `Value::append` where layouts permit; rank, key or name changes → ordinary catenation. Modified destructuring calls modifiers left to right; ordinary destructuring assigns right to left. An assignment's RHS runs once.

Each, Rank and outer products call their operand via `each_pair` (`eval/operators.rs`): one batched call first (`batch::tried`), then once per cell, assembling results by shared layout and prototype rules. A 0-cell keeps an atom or encloses an array item. Custom operands: empty Each, Rank and outer product calls substitute prototypes for empty arguments, in prototype mode; explicit effects stay observable when a call runs; catchable prototype-call failures give prototype zero; interrupt, timeout and unsupported errors propagate; restore prototype mode on success and error. Stencil: Rank over `↕`'s windows, reading its specification through `↕`'s `WindowSpec` (`primitive/structural.rs`).

Rank tries `whole` before `each_pair`. `whole`, in order:

1. one operand call where neither argument has a frame;
2. `decomposed`: `•decompose⍤2` on a stack of matrices factors the whole stack via rustymath's `linalg::Stacked`, as `•decompose` factors one;
3. `whole_cells`, Rank's whole-argument routes, shared with batched calls (`batch::whole_call`), in order: `primitive::stacked` (`⌹`, `-.×` on stacks of inexact matrices via `linalg::Stacked`, as rustymath's Python API runs them); every `f.g` with a rustymath product kernel, on compact stacks of any item kind, via `linalg::Product` (an exact product not fitting 64 bits keeps per-cell calls, which compute exactly); one padded call of a pervasive primitive (`padded_call`); `primitive_cells` (a primitive with one argument, or with a left argument every cell shares); `paired_cells` (matching frames, or a right argument every cell shares). An argument with no axes besides its cells' is the same in every cell;
4. `pervasive_cells`: a pervasive primitive under nested Rank;
5. monadic operand: `cell_rule`, which also takes folds, atops and a bound left argument.

- `primitive_cells` runs a primitive on the whole argument along the cells' axes. A form that `extends` runs whole at a cell rank at least its own. Other forms follow the `cells` fact (`CellRule`) in their `Primitive::info()` row: `⊖ , ↑ ↓ ⌷ #` and rotate-first call their axis forms; `⍉` sends each cell's axes after the frame's; `≢`, `⍴` give constants; a reshape keeping a cell's items in order is a view; `⊂` encloses each cell of rank 1 or more via its axis form, whose cells are views of the argument's items. Any other form with a left argument every cell shares takes `paired_cells`.
- `paired_cells`: joins each pair of cells for `,` and `⍪`; calls a form that extends once where both cells are at least its ranks; first repeats an argument every cell shares over the frame (`agreement::spread`).
- `padded_call`, `paired_cells` leave an argument with a named frame axis to the per-cell path, which pairs frames by name (`named_frame`). Names on cell axes pair in whole calls as per-cell calls pair them.
- A pervasive primitive folds or scans a simple array along the cell's axis (`folded_cells`); `f/∘,` folds all cell axes at once. An atop applies its inner function's rule, then Rank for its outer function.
- Each rule applies only where Rank's mix of the cell results equals the whole-array call's result. Other nested results, and folds by other functions, keep per-cell calls.

Axis nodes select or move axes, reusing Rank where the function has no direct axis meaning. Vector-axis reduction: the general composed-ravel rule, keeping axis order and the whole seed; single-axis reductions keep direct kernels. Layout-only changes share storage. Structural results keep renderers where rank permits; scans and in-place changes copy complete layouts. Match ignores renderers.

Inverse nodes propagate fixed-argument sides through composition. `f⁻¹←g`, `f∂←g` replace the binding with a `Ruled` node: the function plus its hand-written inverse and derivative; calling it calls the function; `⁻¹` and `∂` use the rules; Under counts an attached inverse as keeping every item. Candidate-building primitive inverses validate by applying the primitive again. Inverse scans share forward scan's seed and axis validation. Agenda calls its selector once, then passes the original arguments to the selected branch. Computed operands of Rank, Axis, Stencil and Agenda: shared operand evaluation. Python builds these nodes directly, not by generating source.

Form rewriter (`eval/rewrite.rs`): the one home of fast combinations.

- Rule: a row of BPL text, a pattern over `⍵` and `⍺`, beside the hidden `Special` that computes it (`⍟1+⍵` beside `Log1p`); `rules` adds the selections, one per order and pick. A rule's functions must be glyphs and its constants literals: a name holding `1` or `⍟` isn't recognised.
- The rewriter reads a function and an expression as one tree of calls (`Form`), replacing each subtree a rule matches with a call of the rule's function. `Function::new` rewrites a function's monadic and dyadic forms once, keeping the results (`rewritten`); `dispatch` calls them in the function's place; inverses, Under and display read the original node. `Binder::reduced` rewrites each list of nodes after `joined` and `members_with`. Every spelling, expressions included, takes the combination from its first call. `calls_tines` builds a train whose tines `may_combine` accepts; `Function::new` then rewrites it.
- `combined` runs the structural replacements (selections, ranks, Key's counts and folds) before any running level. An algorithm unsuited to the arguments, or a running level carrying one → `combined` calls the functions the combination replaces, which the level then sees.
- Each combination has a row under "Fast combinations" on its glyph pages. `tests/explain.rs` checks via `•explain` that every documented spelling of a structural combination takes it; `core.bpl` reference cases check each gives what its functions give in turn. The coverage matrix runs each rule whose function maps its argument (`mapping_patterns`), respelling any form's own case a rule would capture (`rewrites`).
- A combination chooses an algorithm, which stays in rustymath or the kernel modules. A whole-array path that follows from an operator's own definition (Rank's for pervasive operands) belongs with the operator.

## Numbers and backend ownership

`number.rs` owns scalar kinds, promotion, exactness, and the suffix table spelling numbers (`e`/`ₑ`, `j`/`ⱼ`, `r`/`ᵣ`, `ₓ`, width marks), read by the lexer, `Number::parse` and display. Ordinary machine integers and the unbounded `ᵣ` integer/rational domain remain distinct. Ordinary integer overflow wraps at the maximum machine width; dynamic kinds retain widening within machine widths. Integer `÷` floors. `÷ₐ` selects float division and `÷ᵣ` selects rational division before computation. A whole `ᵣ` result never becomes ordinary and prints as `3ᵣ`, not `3ᵣ1`. Python/JSON conversion policies stay unchanged, including imported unbounded values. Booleans: a distinct kind; arithmetic reads them as 0/1, logical operations preserve them. Match, search, grade compare numeric value; reference checks also distinguish representation and exactness.

Joining compact arrays widens Boolean → integer → float → complex; float widths join at the wider. Item-by-item construction keeps exact and approximate kinds apart, staying mixed when needed; only approximate real and complex items widen together. A write into an existing array follows the items rule (`Widening::Items`), as a literal of the same items would: exact and approximate numbers stay apart, as do Booleans and other numbers. Rearranging or combining mixed storage finishes in `Gather::finish`: compact where one dtype holds the items under the items rule; its scan compares each item's variant with the first's → a copy that stays mixed pays little. An in-place write into mixed storage keeps it mixed (a scan per write makes a loop of writes quadratic). Fresh computations choose storage from their result path. Results computed one cell at a time (Each, Rank, Key, power histories, polynomial and number-theory functions) assemble as items via `Value::assemble`; mix and catenation join arrays. Keep whole-array joining and element assembly distinct.

`element::Converts`: the one rule converting a compact item to another numeric type; size marks, `•float`, and programs' `Convert` steps in replays and block stages use it. Float target: reads the item as rustymath's `Source` does. Integer target: Boolean → 0 or 1; integer wraps to the width; float → floor within the float width's tolerance, then saturates at the target's range. `Value::converted`: plain values. `derivative::converted`: carried values, through the carrier (`Carrier::cast`); on a pending array, one more pending call (`fusion::convert`).

Bare numbers, empty literals, NaN: the parsed float width. Top-level `evaluate_code` validates the whole syntax, runs leading literal-record `•prefs` statements, then parses the rest at the new width; a syntax error prevents header execution. The default width also covers imported numbers, random data, and float results from exact operands. Time, date and metadata values: f64. Formatting marks non-default widths; serialization marks every float (width-independent readback).

Float operations compute at the wider operand width; exact operands round to the width computed at. f16 operations run on f32 copies when `Numeric::halving` says: a call with an f16 operand, or any call while the default width is 16 bits. `pervasive::planned_halves` applies it to whole operations, `Number::halves` to scalar arithmetic and comparisons; `fusion::defer` declines those calls. Exact inputs convert once, to f32; float outputs round back to f16. The scalar `Number` path rounds each f16 step. Complex parts: f32 or f64; f16 becoming complex uses f32 parts. Scalar Complex32 arithmetic computes at Complex64 and rounds; kernels can compute at f32. These paths needn't agree in last bits.

Floats: IEEE NaN, infinity, signed zero. Comparison: NaN unequal; match and search: one value; grade: last. Exact arithmetic dividing by zero can give those floats. Floor/ceiling keep an exact operand beside infinity; beside NaN the result is open: NaN or the other argument, varying by platform. Their folds, scans, windows, products and repeated writes give NaN or the maximum or minimum of the non-NaN items, never another number (rustymath's `Folds` doc): a loop folding by them passes its running result as the right argument, which `rustymath::reduce::maximum` keeps beside NaN, or folds through rustymath's `Max`/`Min`, as `Dyad::extremum` does. Under dynamic kinds monadic floor/ceiling/sign return machine integers; float-to-integer conversion floors and saturates at the target range. Static unmarked float forms retain floats. Outside `number.rs`, use `Number::float(value, width)` and explicit-width array construction, not implicit f64 conversion.

Static kinds (`•prefs ["kinds":"static"]`): a result's kind follows from its arguments' kinds alone (`meta/kinds.md`).

- `Numeric` carries `kinds` and `int`. Until the `float` pref sets a width, `Numeric::set` gives new floats the kinds' width: 32 bits static, 64 dynamic (`Kinds::float_width`). Whether the pref set one: `settings::float_set`, outside `Numeric` (every call builds and copies a `Numeric`; a Boolean field there cost about 14 instructions per primitive call, 34 per dfn call).
- A pervasive call on arrays plans before computing: `plan::pervasive` builds a `plan::Pervasive` from operand kinds (`plan::Kind`: type, fixed width, weakness) and settings, reading no items. It holds the settings with the operands' fixed width (`Numeric::for_kinds`), whether 16-bit floats compute in 32 bits, the computing kind (`computes_in`: rustymath's `DType::common` after `Numeric::kind`), its kernel table (`computes`) and, under static kinds, every result's kind (`Pervasive::result`). Eager dispatch, fusion's deferral (`Pervasive::fuses`) and typed programs read the same plan.
- Products and folds plan likewise: `plan::Product` holds `g`'s pervasive plan and the settings `f` folds its results under (`Product::folds`); `plan::Fold` a fold's or scan's settings and operand kinds. Eager products, folds and scans read them, as typed programs do.
- Comparisons, `⌈ ⌊` and bitwise functions compute at their arguments' storage width, where results are the same at every width (`pervasive::first_kind`). A comparison of integers with a whole float standing for an integer computes on integers via `Pervasive::computes`; so do a residue by such a float and a residue scan from one, whose results then convert to floats (`plan::whole_float`).
- Weak (`Number::is_weak`): literals, values computed only from literals, Python's scalar arguments. Before a call, `Primitive::weakened` converts a weak number beside a strong one to the width rustymath's `DType::common_weak` gives, or to a fixed integer's width where it fits. Weak integers have no fixed width; NEP 50 decides theirs.
- Loops keep the failed results `keeps` names: floats' NaNs, wrapped integers of objects reporting `WRAPS`. Kernel tables choose float `⌊ ⌈ ×` and wrapping negation from `run.numeric()`. `Stored::build_at` keeps complex results complex.
- `Primitive::number` gives every pervasive result on numbers and each step of a fold of numbers; under static kinds, `statically` converts it to the plan's kind. A static call on ordinary integers that an integer kernel takes runs it at the `int` width, as fixed integers run at theirs (`Primitive::integer_kernel`). Under dynamic kinds a call on two numbers stays outside plans: its result type depends on their values.
- `Number::wrapped`, `Value::wrapped`: wrap an exact integer result to the integer width: the fixed width `Numeric::for_kinds` finds among the operands, or `int` under static kinds. Under static kinds a strong ordinary integer is a fixed integer of the width it computes at, `int` joined with its storage width (`plan::Kind::stored`) → every static call on integer arrays computes under a fixed width. Display marks a fixed integer of `int` width with plain `ₓ` (`Mark::integer`).
- A fixed kernel failing where a result doesn't fit (lcm, binomial coefficients) gives the exact result wrapped (`Primitive::fixed_number`), used by `statically` and by exactly computing functions (`⊥`, `⌻`, the determinant). Where integers wrap, a function with approximate results (`⌹`, polar parts) computes integers as floats of their float division's width (`plan::Kind::approximate`); `∂` converts its argument's wrapping integers to those floats before running its function (`derivative::differentiate`). `Number::parse` keeps complex literals and checks integer literals against the `int` width.

Settings: once per process in `settings.rs`, read from there, not passed through functions, except where a read is slow and on a hot path. Atomics: each setting calls and scalar operations read: numeric settings, hanzi aliases, the `batch` pref, the verifier flag, the fusion report flag, fusion's sizes (`settings::set_sizes`), the compile setting. Display settings: behind one lock. Writers: `•prefs`; the lexer, for a source's leading `•prefs` header as it reads it. `settings::reset` restores defaults (`]clear`, test harnesses). A module `•load` runs changes settings process-wide; nothing restores them on return. Thread count: held by rustymath, the one setting it reads itself; `•prefs` writes it there.

- Each call reads the store once, at its start: pervasive calls, folds and products as they plan (`Primitive::pervasive_mapped`); a dfn call as it looks for its program (`program::call`); `Domain::of`; the lexer. Values derived from settings within a call stay explicit arguments.
- A call's plan holds the settings it computes under → a pending array computes under its calls' plans, whatever settings are in force then. A pending conversion holds the settings giving its floor's tolerance (`Step::Convert`'s `numeric`). A dfn's programs are found by the settings they were traced under (`program::Key`); under other settings the dfn traces a new program.
- Passed explicitly: loop structs keep the settings (their closures run on rustymath's worker threads); `Number`'s tolerance methods and `Primitive::number` take them (once per item); the parser's leaves take a width marker's width; `matches_within` takes `⍣∞`'s convergence tolerance.
- Imports build complex numbers with `Number::complex_in_session`: Python's `_Session.array`, the JSON protocol's `request`. JavaScript values hold no complex numbers.

`Numeric::mathish_at(width)` owns Mathish eligibility: preference on, kinds dynamic, calculation ordinary exact, f64 or complex128; fixed-integer operations excluded even at f64. Kernels select their numerical objects, from rustymath, before the loop. Mathish comparison tolerance `1E-14`; f32 and f16 compare exactly. Fixed-point convergence: four ulps at those widths, `1E-14` at f64, independent of Mathish. Index, count, Boolean and character-offset conversion: `near_integer` with the fixed default tolerance. Test with independent inside- and outside-tolerance cases and exact/mixed controls, not language comparison as its own oracle.

`search.rs` selects compact exact or tolerant backends.

- Classification of 1,024 items or more first groups items sharing one array, before reading any (`search::shared_classes`). Imports make repeated texts share: `keyed::Texts` makes each distinct text once per `•csv` column, `•json` document and Python conversion, up to 65,536 distinct texts.
- Exact integer, Boolean and character storage uses keys; float searches use their width. Integer haystacks take the whole-number shortcut only for exactly whole float needles. Tolerant indexing validates whole-key matches unless the haystack is exactly whole, falling back to buckets on mismatch. Classification chains tolerance through sorted runs by design: it needn't match every member to one representative. Other cells: exact hashes or first-number buckets with `Value::matches` confirmation; pairwise comparison where indexing is unsuitable. Grade is stable.
- Position buffers: u32, becoming integer storage without another pass. `⍷` and monadic Key take each class's positions from `search::class_positions`, which keeps a class's own buffer for 32-bit positions and copies narrower ones once from the shared buffer. Dyadic Key selects rows through `Groups::each` slices. Key's group-fold idiom folds through `search::numbered`'s class numbers; where `fold_groups` declines, Key builds positions from those numbers. Key with operand `≢⊢` (also built by `≢∘⊢`) counts classes via `search::class_counts`, building no positions.
- Under Rank and in batched maps, `⍳`, `∊` and `⍸` whose haystack differs per cell search each cell's own haystack in one call on the whole arguments (`primitive::searched_cells`).

`Domain`, `with_field!`: select working reals, Complex64 or BigRational for generic numeric algorithms; compact storage selects the domain without scanning items. `number::read` converts once; `Field::array` builds compact float or complex results without a `Number` per item. Each caller lists the domains it supports. Compact complex input doesn't take a real path merely because all imaginary parts are zero; results built via `Value::complex` can normalize to float storage.

Rustymath owns mathematical algorithms; basedpl owns pervasion, storage, numeric promotion, axes and language policy. Code whose inputs and outputs are only buffers, shapes and plain numbers belongs in rustymath, even if only basedpl calls it. Approximate matrix solve, pseudoinverse and decomposition: rustymath factorizations; on macOS rustymath sends much of it to Accelerate (its DEV.md); no platform-specific adapter here. macOS deployment minimum 15, set by the Cargo configuration (Cargo's builds) and `pyproject.toml` (wheels). Exact solve, pseudoinverse and determinant: rational field algorithms. Generic permanent and polynomial helpers also run at floating and complex field types. Singular or wide matrix division: least-norm solutions. LU eligibility and SVD cutoffs: rustymath policy, not duplicated here.

Hash maps and sets: `rustymath::hashing`'s `HashMap`, `HashSet` and `Hashing` (rustymath's DEV.md), not another hasher → every lookup in both projects inlines its hash the same way.

`•decompose`/`•decompose⁻¹` share domain reading and `Factor` dispatch, with options for kind, vectors and complete QR. Polynomial adapters: compact evaluation or generic field operations; gradients differentiate coefficients before evaluating. Number-theory adapters: cancellation checks, result cell assembly. Distribution constructors expose native density, CDF, quantile and sample functions; compact continuous calls use slice objects; discrete samples and finite discrete quantiles are exact integers.

`•rand seed`: a key and a count of draw calls behind a mutex (`rustymath::random::Counter`), shared by every copy of its record. `¿`, and a distribution's `sample` without a generator, draw from the session's generator; `•prefs ["seed":n]` reseeds it. Draw call c reads stream c under the key from its start. Item k of a call reads its packed words, then its own region (`rustymath::random::Items`), so an item reads the same words on every route. The algorithm is fixed, but range or distribution sampler changes can change draws: the reference sequence detects that. Sampling from a generator record uses its roll function to recover the same generator.

## Kernels, fusion and threading

Dispatch selects a primitive before its loop; a pervasive call's plan picks its kernel table (`plan::Pervasive::computes`). Concrete `Kernels` tables call rustymath objects: `many` for slices, `one`/`checked` for scalar Numbers. `at_widths!` writes f32/f64 tables once. Arithmetic, circle-code conventions and scalar policy stay in the numeric modules; no second evaluator.

Mixed item types: `Converting` where the object loops item by item in rustymath (`Results::INLINE`), converting each item as read; else `Chunked`, reading each argument through rustymath's `Side` a converted run at a time into one homogeneous implementation → no storage-type cross-product of machine code. Compile only operand pairings that can occur. Same-type arguments can reach rustymath in one call; other shapes expand reused chunks or use block mappings, avoiding per-item division.

Custom elementwise closures: `rustymath::pairs` and its uninitialized append path; function objects use their own slice forms. Keep per-item bodies inlinable across codegen units: a closure passed by reference can add an uninlined `Fn` shim → pass it by value, or wrap the reference in a new closure. Hot loops: slices and fixed chunks, not iterator helpers that add calls in the incremental build. Avoid captured mutable flags held in memory: they block vectorization.

A failed compact kernel leaves placeholder results and reruns the whole call on a wider, exact, complex or scalar path; complex fallback shares `Number` policy. Overflow detection belongs to rustymath: its arithmetic objects' integer forms, checked reductions, checked products. Cheap integer multiplication picks an exact width from bounds, with no per-item overflow check. No blanket NaN or signed-zero canonicalization pass; algorithm-specific failure checks and rustymath's SIMD kernels stay inside their algorithms.

Fusion (`fusion.rs`; its module doc owns eligibility rules and limits: don't copy its thresholds here):

- Calls a block stage can run (`plan::Pervasive::fuses`) defer: `Primitive::pervasive_mapped` returns a pending array (`Data::Node` holding a `fusion::Pending`): a typed `Program` of its one step, plan fixed at call time, plus the arrays and atoms it reads, each pending one in its own value (`fusion::held`). Pending arrays survive assignment and link to the pending arrays they read. Node-making code stays out of line from dispatch: inlined, it grows the frame kept on the stack at every recursion level.
- A read forces via `ArrayData::storage`: gathers in the programs of pending arrays it reads in order (`Pending::gathered`), runs the result through its plan's units. `program::planned` plans each program structure once, from a copy with inputs for held arrays, reusing the plan for later forces of the same chain on new arrays. Shape, kind and prototype readers (`Value::len`, `Value::environment`) don't force. `Value::force` forces, as timing does.
- Fusion and dfn traces both add nodes via `program::add`, which returns an earlier node making the same value: a held atom of the same identity, the same held array, or the same step on the same values.
- A pending array read in order that a name or another array also holds joins as an output (`Program::outputs`), computed in the same pass; a block stage stores its items with the result's. Other pending arrays the program reads but doesn't compute as steps compute first, alone (`Pending::gathered`): those not readable in order, and held copies. A fold of a held pending result stores that result as an output of the fold's pass, once for all readers (`fusion::fold`); a pending copy folds so, held or not.
- A block stage runs elementwise steps block by block, in parts (`blocks::Part`): each run of steps lowering to machine operations that give their kernels' exact results (`blocks::lowered_op`) through one compiled kernel (`jit.rs`); other steps through the same pervasive kernels (`pervasive::node`). A part whose kernel can't take a run's items (e.g. an input a broadcast reads as one item) runs those kernels for that run. A stage compiles all parts or none: where the same kernel compiled or ran before, or where one run of its items repays compiling (`blocks::Blocks::compiles`, `repays`). `settings::Compiles` can compile every stage or none: the reference harness; timings via `BASEDPL_COMPILE`. A call waits where fusing it saves more than its node costs (`fusion::waits`: `NODE_NS`, the allowance per call, against `SAVED_NS_PER_BYTE`); `BASEDPL_DEFER=all` makes every call wait, for timing what a node costs.
- Each step writes a block to a buffer later steps reuse once its readers ran. A comparison read only by later steps of the stage writes floats 1 and 0 there (`Dyad::compared`, rustymath's `tolerant::Indicator`). `⍚` and `@[p]` run cases that can't fail on every item, selecting by a Boolean mask (`selected`, `eval/operators.rs`); `plan::select` gives its type and the maps its mask and cases read through; `fusion::select` defers it where the mask is such a comparison, else runs it at once via rustymath's `chosen`. A one-step stage runs only where it reads through a copy, recording no `fused` row.
- A structural copy of one source through rustymath `Steps` (`remapped`) large enough to wait (`fusion::waits`) is a pending copy (`fusion::copy`), any compact kind; its map is a `Mapping::Steps`, one entry per result axis, as broadcasting's are. Forcing composes a read of a copy with its map and moves a read with no repeat or fill under the pervasive calls it reaches (`fusion::resolved`): `2×⌽v+1` reads `v` backwards in one program. A copying read (rustymath's `Mapping::copies`) moves only under a one-array call. A call whose two array arguments copy same-layout arrays through one map runs on those arrays, its result copied once (`program::rules`, `copy_lifted`). Other arrays: a `Copy` step, which a block stage reads through without making the copy. A step reads items in order under another shape through its operand's `program::Read`.
- A block stage shrinks blocks whose buffers wouldn't fit in cache. Rustymath's `agreement::expanded` reads a forward run in place, else copies via `gather::walk_plan`. A `Mapping::Steps` keeps the plan `Steps::simplify` makes on its first walk (`agreement::Route`) for every later block. A copy no call reads through is walked as `remapped` walks it.
- Fused and ordinary folds share rustymath's `reduce::along`/`fold_into` traversal. A block stage of one compiled part folds the last step's items itself, handing `reduce::fold_pieces` each block's total (`reduce::Part`): sums, float products, maxima, minima. A float fold keeps as many running results as rustymath's folds (`reduce::running`). Boolean folds, float `⌈`/`⌊` folds, and blocks crossing a lane go through the last step's block.
- On the pending route, a fold of a windows copy along its own axis slides over the copy's source (`pervasive::slid`, `mapped_fold`: rustymath's `reduce::fold_route` with the copy's source, `structure::Slide`, `reduce::sliding`); a fold along two window axes folds both in one pass (`sliding_2d`). A short fold a stage folds as one step per window position (`blocks::short_window`) runs as a block stage reading the copy's source at each position through the copies' maps: in a dfn's program, and on the pending route where the copy reads another pending copy (e.g. padding) into a result whose last axis exceeds `DIRECT` (`fusion::staged`). Under `∂`, `fold_rule` takes a maximum's or minimum's positions in such windows from the source (`pervasive::mapped_picks`); under a trace, `Step::Picks` gives each lane's pick, via the untraced mask's function (`derivative::chosen`). A traced `⌈`/`⌊` scan, or picks from sliding windows, stops the trace.
- Ordinary pervasive kernels read pending copies through their maps: `fusion::source` snapshots source and mapping without taking the pending work; rustymath composes that mapping with the call's agreement; `pervasive::Input` keeps the snapshot alive while existing blocked readers read its storage. Rustymath-reduction folds read pending copies via `fusion::source` too (`pervasive::mapped_fold`). `reduce::along_mapped` folds a copy reading a contiguous source block with reordered axes (per `Mapping::block`: transposes, reversals, non-overlapping windows) in the block's own order; totals in another order become a copy through `along_mapped`'s tables (`pervasive::fold`), which the next fold reads as a block again. Other copies fold a run at a time where runs reach `reduce::RUN` items, uncopied; else a piece at a time, copied. A held copy read in shorter runs (`reduce::rereads_cheaply`) folds from the copy `native_fold` computes and keeps for later reads (`fusion::held_copy`).
- A read of a few items goes through `fusion::narrow`, narrowing the pending work to the positions read without consuming it: a chain of copies → a read of its source, any item kind; an elementwise call, or a fold's leftover program, → one over those positions only, on its first nonempty partial read of at most 1 in 128 of its items, shared or not. Where maps don't compose (a rotation with an overtake carrying source items across the end), the read lists its items' offsets. The original keeps its work; its next full read computes and caches the whole result. Copy unwrapping, empty and all-missing reads don't count. `fusion::item` serves single items and picks; `Gather::walk` small copies and gathers via `fusion::walk_through`. Whole-input value checks (bounds, finiteness) read only items its logical `ArrayView` selects. Unsupported compositions and dense readers keep the pending array's one cached compact result.

`explain.rs`: events `•explain` reports. One check in `Function::reported` serves `•prefs ["fusion":$t]` and `•explain`: a call computing a pending argument writes the pref's line and records `forced`. `Blocks::run` records a fused group per block stage of two or more steps, fold included; `Idiom::call` each fast combination taken, by `Idiom::route`. Nothing emits rustymath's `Accumulation` or `Mixed` events, and nothing counts live record nodes or pending arrays, so `•memory`'s `records` and `pending` are always 0 (`open.md`). `•explain` and Python `rm.explain` use the `rustymath::events` capture: each native module captures its worker threads through one process-wide sink; captures can nest on one thread; the shared `Route` declaration supplies fast, decline and fixed itemwise IDs and their coverage inventory. Successful routes aggregate call and item counts. Optional declines stay separate from stopped traces, which record a slow fallback on every execution, cached failures included. Outside capture a native event checks one atomic flag. `Value::footprint` walks a value's allocations for `•memory`'s `bytes`.

`∂` (`derivative.rs`):

- Dual: tag, primal, tangent: a `transform::Carrier` in `Value::Carried` (number) or `Data::Carried` (array); primal and tangent can be pending. A record of linear calls is the other carrier.
- Routing (`transform::call`) sends a call to the newest level among its arguments (`Value::newest`), reading their outer layer; a newer level inside an argument in mixed storage wins (an array of dual atoms beside an older dual). Newest level a `∂` call → `derivative::call`, run by the form's facts in `Primitive::info()` (`primitive::Facts`): a pervasive form's partial derivatives run as primitive calls, from the recipe of the function object the kernel table picks (`partials`, `pervasive::Dyad::differentiable`, `rustymath::derivative`); `⌻` has its own rule; forms whose results carry no tangent run on primals.
- Structural glyphs, Under and selective assignment need no rules: their code moves each part of a carried array through the carrier's moves (`Carrier::view`, `Carrier::at`, `Carrier::copied`; writes: `transform::written`, which a record answers through its ids). `Gather` copies a dual's primal and tangent together (`derivative::Join`).
- A glyph copying its right argument through one plan, and a broadcast, copy a record tangent as one `Op::Copy` (`primitive::copied`; `Form::Moves`'s `planned`), holding the plan's `Steps` as a rustymath `Mapping` (`Mapping::walk`), as pending copies and `Step::Copy` do. Its transpose reads through `linear::transposed` (rustymath's `Walk`, `Steps`): the inverse map for a copy reading each item at most once; a correlation for windows moving by 1. A copy of a copy transposes in one read where the composed copy still transposes by reads (`linear::composed`); maps compose via rustymath's `Mapping::through`, as in fusion and traces. The record keeps the chain: recognising windows needs each copy's own shape. A sum along a window axis transposes as a sliding sum (`linear::slide`); a spread axis as a sum along it. Windows moving by more than 1: rustymath's `signal::overlap_add`, adding each window back where it read (`linear::strided_back`). Other copies, and copies of several sources, keep ids and scatter.
- Rules: reverse mode's `⌈`/`⌊` fold: the tangent times a mask of each lane's chosen item, summed; its transpose reads. Mix of a dual with a nested primal mixes primal and tangent apart. `fold` and scans with `+ × ⌈ ⌊`, `+.×` and outer products have rules; kernels reading numbers directly leave active arguments to general paths. Folds by primitives, products of primitives, `⌹`, `⊥` and stacks of matrices route through `transform::call` as operations (`primitive::Operation`): their rules (`derivative::solve`, `decode`, `product_dual`, `determinant`, `fold_dual`) run on a `&Context`, calling `Operation::call` for needed products, folds and inverses. Rank's whole-argument routes send carried stacks through `Pairing::Matrices` → `⌹⍤2`, `+.×⍤2`, `-.×⍤2` take stacked rules in one call, `batch` on or off. Attached rules, system functions, and folds and products by non-primitives take the same `transform::call`, as `transform::Op`'s other variants.
- `⌹`, `-.×` keep the glyph's own result as primal → same values with or without `∂`. Tangents and transposes multiply by `R`: the inverse `numeric::matrix_inverse` takes from one factorization via rustymath's `Stacked::inverse`, or exact row reduction for exact matrices; `regular_inverse` gives UNSUPPORTED where rustymath's regularity test finds the matrix singular. Only `B` active: `R` is `⌹A`, pseudoinverse included.
- One number in `x`: `f∂ x` runs `f` once with `x` seeded. More: `linearized` pushes a record level just below its `∂` call's level, runs `f` once with each part of `x` seeded with a record at it (`linear.rs`): a tangent whose items are never computed, which the same rules extend into a graph of linear calls. Newest level a record level → records the linear map its form's facts name (`linear::call`). `reverse` reads the Jacobian from the record: a transpose per result item or a forward evaluation per number of `x`, whichever fewer.
- An `f∂←g` JVP rule is called with `⍺` a dual of zeros whose tangent is the argument's → in reverse mode it extends the record (`derivative::attached`). Such a function called dyadically: DOMAIN ERROR wherever `∂` needs a derivative through it (`derivative::two_arguments`).
- Code reading a dual array's storage gets dual atoms (correct, per-item speed). A rule packs an array holding its level's duals, at any depth, into one dual before splitting it (`derivative::packed`). Readers outside a call use `transform.rs`'s read point: `Value::observed` (counts, positions, ranks, selectors, `≡`, guard predicates) reads a dual's primal; `Items`' integer readers read carried items through it (`Value::observed_number`). Its `Result`'s error, `transform::Stop`, names the level owning a batched run. A stop is `ErrorKind::Stop`: no guard catches it, even one naming it; catch-all handlers let it pass (`ErrorKind::is_control`). Display reads via `Value::displayed` (never inside a batched run). `Value::computed` (kernels, via `primitive::numeric`) gives UNSUPPORTED for a dual atom.
- Writes to bindings outside a `∂` call are recorded and stripped when it returns.

Typed programs (`program.rs`, `program/`), run by pending work and `∂`:

- `∂` of a dfn runs one program holding its whole call, value and derivative (`derivative::differentiate`). The first call with given argument types, layouts and settings traces it (`program/trace.rs`): the dfn runs on traced values (type and layout, no items); each call plans its result (`plan`) and adds a step via `program::add`. Where the trace stops (`nbs/autodiff.qmd`, "What stops a trace"), the call runs in the interpreter.
- `Programs` keeps each trace's outcome, program or stop, on a dfn's `Definition` or another function's structure (`program::Tacit`, at most `STRUCTURES`). An outcome serves later calls with the same argument signature whose free values still hold what the trace read (`Entry::reread`) → cycling free values replay. Free values changing every call stop tracing after `CHANGES` traces in a row; a function keeps at most `KEPT` outcomes.
- `program::call` replays the program on the call's values; `program/run.rs` replays step by step, the reference compiled code matches. Fusion's and traced programs share this code.
- Index notation and its gradients: `Step::Gather` selects by computed positions; `Step::At` writes or accumulates where a map or selector says; `Step::OverlapAdd` adds a windows copy's cotangent back to its source; `Step::Picks` marks each lane's `⌈`/`⌊` fold pick. Level 2: rustymath's selection planning (`structure::joined`) reads an index array with affine positions through strides, not an offset table (`Table::affine`).
- `program/contraction.rs`: a `+` fold of a `×` whose operands read sources through affine maps runs as one product (`contracted`); a fold of a copy repeating items as a fold of its source (`fold_of_copy`). `program/layout.rs`: stores maps in the order operands and readers need (`layout::ordered`). `blocks::plan`: finds runs of elementwise steps for block stages. `program/verify.rs`: checks each program's contracts before it runs, in every reference case and page (`settings::verifies`).
- `•explain` lists programs a call built or replayed, and stopped traces (`programs`, `stopped`, `declined`). `["sites":$t]•explain` fills `site` on `forced` and `stopped` rows: the innermost basedpl functions that computed the items or stopped the trace (`explain::site`, from a Rust backtrace, skipping the event's own bookkeeping, `BOOKKEEPING`). Use it to place a forced read or a trace stop, rather than a temporary backtrace.

Batched maps (`batch.rs`):

- `batch::tried` (from `each_pair`): begins a batched level (`transform::Kind::Batched`), wraps each framed argument in a `Batch` carrier at it, calls the operand once, ends the level. A map first lays its arguments over its frame by its own agreement, the pairing its per-cell calls read (`batch::Arguments::laid`, `agreement::laid_cells`). One cell of atoms: no batched call (faster).
- Routing sends calls whose newest level is the run's to `batch::call`: primitives, operations primitives name (a fold by a primitive, `+.×`), operations by dfns. `⍕` and random draws keep their own code; other system functions run per cell, results joined into one batch (`batch::system`, `batch::each_cell`). `batch::call` runs whole arguments by Rank's routes (`eval::whole_cells` via `batch::whole_call`; `eval::folded_cells` for folds) → a primitive batches wherever Rank runs it whole.
- Folds and scans `folded_cells` misses (e.g. by a dfn) run the fold's own loop over the batch's items, one call per stage on item `j` of every cell (`Batch::at`); `fold_array`, `primitive_fold` join stage batches into one (`joined`). Every fold and scan route decides structural cases (unit, empty lanes, result shape) in `FoldPlan` and ends in `folded`, the only place giving the result its layout, fused folds included. Folds and scans by non-primitives over several lanes try their own batched run: `operators::by_lanes` moves the fold axis last and runs the derived fold over lanes via `batch::tried`; `operators::by_triples`, for `f.g` with non-primitive `g`: one batched `g` call on a frame of rows by contraction by columns, then the `f` fold along the contraction, per chunk of rows whose triples hold at most `batch::CHUNK` items (`operators::by_rows`, shared with products of primitives). A try giving `None` → the usual loop from the start. A fold keeps its stops on its operand's `Definition` (`Function::remembers`).
- Stops: `batch::tries` holds every try's conditions. A call no route covers stops the run (`transform::Stop`). Constants with axes that, spread over the frame, would exceed both 4× the arguments' items and `batch::CHUNK` (2²¹) items stop it, naming a chunk of cells whose share is at most `CHUNK` (`oversized`, `Stop::chunk`); `tried` then runs the operand once per chunk (`batch::chunked`), each a batched level on a one-axis frame, joining results as the per-cell run would. A chunk stopping for size restarts with its own smaller chunk. One cell's share alone over `CHUNK` → one call per cell.
- Code that must run once per cell asks the levels first (`Levels::effect`): output, input, `⍕` of a carried value, acting system-function code (`Effect::Acts`, via `Context::acts`); a guard or prototype call that would catch an error (`Effect::Catches`); a write outside the map's frames (`Effect::Writes`, via `Levels::record_write`). An observing read (`Value::observed`: a count, a position) stops the run too.
- A guard on a batch of the run splits it (`Session::guard` via `operators::guard`): `batch::truths` gives each cell's Boolean; each side runs once as a guard case on its cells (`Levels::case`), through `⍚`'s `Cells`; batched bindings of the run's frames read at the side's cells (`Session::restricted`, via `batch::read_cells`, `operators::cells_at`); `Cells::assembled` joins the sides. In a case, the run's frame is the case's cells, random draws draw for them, and a write to an enclosing frame stops the run.
- A map inside the run, the run innermost, widens it (`batch::Entry::Widen`): a case with no definition, frame = the run's frame then the map's; the run's batches among the map's arguments lay over it (`batch::laid_over`); bindings made before the widening lay over it when read (`Session::read_binding`). A widened run that stops, or an Each with array results, falls back to per-cell calls inside the run. A dfn guard already splitting cells in another frame stops the run as recursion (`Cause::Recursion`); sides differing in layout or kind stop it as a call with no rule.
- Each stop carries its cause (`transform::Cause`), setting how long a dfn operand remembers it (`Cause::kept`): effect, write, observing read, recursion: always; no covering route: while later calls repeat argument kinds and cell shapes; memory guard: while they also repeat the frame shape; caught error: never (it depends on cell values). `Definition::remember` holds `ALWAYS` or an argument signature (`batch::signature`), each with the cause (`batch::holding`). A covered later try falls back without calling the operand, with an `"an earlier stop"` event naming the cause. A stop's `fallbacks` event names its cause (`Cause::reason`) and, for an uncovered primitive call, the glyph (`Stop::refusing`).
- Code with no batch rule reading a batch's items gets item carriers (item i of every cell) and records an `itemwise` row, route `"batched items"`. `explain::itemwise`: the one helper for item-at-a-time routes; the innermost call claims the counts (`Function::reported`), as for `forced`. A kernel then reading a number meets the stop `Carrier::computed` gives a batch → a missed reader costs speed or a fallback, never a wrong result.
- A batched run can also start inside a `∂` call: its level is newer than the `∂` tag → batch rules take each call first; their whole-array calls reach the derivative rules. A batch's whole can carry a dual (kind checks read `Value::template_dtype`). Stacks of matrices whose wholes carry a dual take derivative rules via `Pairing::Matrices` (`eval::whole_cells`): stacked kernels read compact storage. `∂` inside the run differentiates by batches of atoms or arrays: `derivative::numbers` counts a cell's numbers from the batch's template; all cells share each direction's seed; the Jacobian joins into one batch (`batch::joined`). A planless move on a dual whose primal is a batch runs on primal and tangent apart (`derivative::apart`). Adjoints a transpose adds into a batch add as one sum on its whole (`batch::scatter_add`). An attached rule runs on the whole batch at its argument's `∂` tag (`batch::call`); `batch::split_whole`, `batch::dual_of_wholes` keep the newest level outermost.
- Random: a map's draws read streams that the outermost map's count, each map's place, axis by axis, and the draw's place among its cell's draws pick (`distribution::map`, `distribution::cell`, `rustymath::random::Key::folded`); a batched run's cells take their places from its frame. Batched and per-cell runs draw the same numbers, under a splitting guard too; a batched run in chunks that draws falls back to its cells. A batched try outside any map that falls back restores each generator's count (`distribution::settle`).
- The result must be a batch at the run's level, a strand of batches whose kinds join (`joined`), or a carrier-free atom or compact array as every cell's result; else fallback. A pervasive call stops where its result kind differs from the one kind a route gives every item (`pervasive::expected`) → each cell keeps its per-cell kind.
- `reference::check` runs each reference case with `batch` off, on, and on under fusion's small sizes (`fusion::Sizes::SMALL`), comparing storage kinds with the first run's.

Folds: rustymath owns numeric folds, scans, adjacent pairs, grouped reductions and integer bounds; basedpl selects kernels, tolerance, seeds, storage widths and exact fallbacks. Rustymath's `facts!` table gives, via `pervasive::folds` and `truth_fold`, the reduction folding each primitive, the object by whose rule each takes characters, the comparison objects `with_comparison!` makes, and the product kernel each pair `f.g` names (`pervasive::known_product`). Folds by algebraic float operations can regroup. Contiguous subtraction and division folds use `Alternating`; quotients fall back to item-by-item folding if their products leave the normal range. Boolean scans compose truth-table maps; comparison scans compute both possible totals in bulk and use `reduce::chosen`. Seeds, axis lanes and scalar fallback keep the language's accumulation direction. Generic reductions stay right-associated, keeping operand call order and effects; exception: monadic `f.g` memoizes each minor's expansion, and a cached minor repeats no operand calls or effects. Determinant and permanent fast paths use the appropriate rustymath backend.

Threads: the automatic Rayon scheduler serves rustymath's elementwise `many` and `pairs`, broadcasts via `agreement::blocks`, folds via `reduce::along`, block stages and matrix products. Scans don't split. Decompositions split in their blocked updates' products, their Hermitian and bidiagonal reductions' passes, and their divide-and-conquer merges.

- `rank` sends dyadic `+.×` and `⌹`, monadic `⌹` and `-.×`, and `•decompose` over the 2-cells of an unkeyed compact stack to `primitive::stacked` and `stacked_decompositions`, each cell through the rustymath function it uses alone. A pervasive operand, or Rank nested down to one, runs as one call: each argument gets length-1 axes after each level's frame → leading-axis agreement pairs frames with frames, cells with cells. An argument with a named frame axis goes through a batched map instead, whose frame carries no names → names pair only between cells (`batch::tried`). Rustymath's `parallel::stack` splits whole cells across threads in rounds, with its interrupt check between rounds.
- `Context::check` reads the clock only on every 64th call → a caller whose checks run far apart calls `check_now`.
- The scheduler adapts to call cost: `RAYON_NUM_THREADS` by default; one process-wide override via `parallel::set_threads` (0 default, 1 serial), which `•prefs ["threads":n]` writes directly. The timing harness sets one thread after each settings reset. Nested Rayon work doesn't split again; wasm is serial.
- A block stage splits in pieces of whole blocks: elementwise via `parallel::extended`, folded via `reduce::fold_pieces`. On one thread an elementwise stage appends straight to its result (copying each block into a piece's slots cost up to 1.2 copies there).
- Small converted chunks limit the scheduler's work: don't infer multicore execution from a large array alone.

Products: a pair with a rustymath product kernel (`+.×`, `⌈.+`, `∨.∧`, `+.=`) runs via `linalg::Product::run`, which Python's `inner` also takes (`pervasive::known_product`). Other native pairs: its bounded `inner_with` runner and `reduce::right_fold`, carrying the right tail across blocks; basedpl supplies primitive kernels, tolerance and the exact-widening fallback. An integer product not fitting 64 bits gives way to the exact path.

- `pervasive::inner` takes each operand's `Orientation`; float and complex products read a transposed operand in place, as reverse mode's `product_transpose` needs.
- A float `+.×` whose operand is a pending copy, or a view of one, hands rustymath's `Inner::inner_mapped` the copy's source and map (`fusion::source`, `pervasive::mapped_product`). A `+.×` whose operands are both pending conversions of compact `u8`, `i16` or f16 arrays to a wider type reads those arrays; rustymath's kernel converts each item as it packs it (`fusion::widened`, `pervasive::widened_product`). A dfn program leaves such a conversion pending for its product (`Unit::Pending`).
- Rustymath gives gemm an operand its map reads at strides (a transpose) where it lies (`Mapped::matrix`), and reads any other copy a block of rows at a time, except in a one-column product whose copy's rows are adjacent in storage (a vector, a single-channel image), where it adds each column of the copy where it lies (`linalg::by_columns`). Neither builds the copy. A copy a name holds is read again for each product, not cached.
- Reverse mode reads a windows copy's cotangent back through rustymath's `Transpose` (`linear::read_back`): one read for each position in a window, a correlation, with fills between frames that move by more than 1 (`structure::correlated`), as a transposed strided convolution reads its cotangent. No scatter-add or zero-padded copy of the cotangent is made.
- Structural gather and compress and interval index also reuse rustymath. Measure changes to generic or backend code in both projects: the callers' codegen and layout decide costs a kernel measured alone misses.

## Evaluation and frontend boundaries

`eval_with`/`call_with` install `EvalOptions`. Echo (default true) off suppresses implicit display, not explicit output or display commands. Output: ordered `Output { kind, data }` MIME bundles, to an optional sink as produced, else retained by the evaluation. Values, functions, operators, outputs and errors stay separate results.

`Execution::begin` puts each evaluation's interrupt handle, deadline and poll in `execution::STOPS`, a static every thread reads; its `Running` guard restores those of an enclosing evaluation (e.g. the one calling `⍎`). `execution::stopped` reads them; the first evaluation installs it as rustymath's interrupt check (`rustymath::interrupt`) → rustymath's long computations (exact matrix functions, primes, stacks of matrices) stop for basedpl's interrupts and deadlines, on its worker threads too. A thread without a turn (e.g. Python's `in`) also stops at the running evaluation's interrupt.

Evaluation code reads the process's one session via `session()` and takes a `&Span` where it reports errors. Boundary checks and long loops call `execution::check`: counts down a static before reading clocks and flags or calling the poll hook; takes no span or session; turnless code (Python's `in`) calls it too. Single BigInt operations and bounded native kernels aren't preempted. Session state sits in `Cell`s and `RefCell`s whose methods return owned values → no caller holds a borrow while a dfn evaluates (`meta/session.md`). An optional `Input` supplies `⎕` and `•nget "-"`; without one they raise IO. Python cancels cooperatively. The process worker can kill an unresponsive process after a grace period, losing its state; requests are never replayed.

`Session::call` resolves and calls a function expression on existing arrays, with no temporary argument bindings; retained functions use `call_function_with`. Spans: `Function::call` gives each spanless error from a function's code the call's span; evaluator errors take the spans of the nodes they report; a statement gives any still-spanless error its own; errors outside an evaluation (e.g. Python indexing) have none. Diagnostics display with Unicode width. Python translates spans to character offsets; process JSON keeps bytes. Native function and operator handles cross the in-process Python boundary, not process JSON.

### Python

`python/basedpl/__init__.py` owns the shared `bpl` workspace and the `Array`, result and error wrappers. An `Array` with a function item is a `FunctionArray`, chosen by `Array._classify` in `__init__` and after `__setitem__` → `callable()` is false for every other array. `fn` aliases `bpl.fn`; builtins and magics share the workspace; registering the magics gives it the REPL's display defaults (`Session::make_interactive`). Plain calls print explicit output and return Array, Function or Operator values; capturing calls return `Result`; capture mode is positional-only (keywords bind BPL names). `_Session.eval`, `.call`: the PyO3 entry points; `request`: their internal Rust helper.

`functions.py` builds native nodes and lazy exports from Rust metadata. Builtins win name collisions with workspace names; operation names choose valence and currying. `__all__` omits Python-builtin collisions; explicit imports still work. Keyword calls use a keyed left argument. One positional argument stays the right argument unchanged; zero or several form a vector. Operator properties and `_Pending` assemble native nodes, never generated BPL source. `printing.py` reads node parts without evaluating or resolving names.

`.fn()` keeps a late-bound expression: calls resolve affected nodes against the calling session, sharing unaffected graph nodes → primitive fast paths, inverses and reduction identities survive. The binder still resolves ordinary names during execution. Cyclic resolution: LIMIT error.

Arrays keep native values; `.py` and `.np` copy; NumPy is optional and lazy.

- The native `_Array` buffer export lends compact items read-only. An unbuilt structural copy with an affine read (`Value::affine`) lends its source's items with strides → windows reach NumPy unbuilt. `own()` moves compact items into a writable NumPy array where nothing else holds them, Booleans as `u8`, characters as `i32` (NumPy can write any bytes).
- Numeric buffers import with one copy via `rustymath_buffer::read_array`; `Value::imported_buffer` keeps supported item widths; the shared reader normalizes signed bytes, wider unsigned integers and foreign byte order. Sibling snapshots carry keys and names. A NumPy uint64 array with a value above int64's range imports item by item as exact integers. Exact integers and fractions cross as native integers, not decimal strings. String and object arrays convert per item.
- Python data converts in Rust: the session's `array` (`import`, `py/src/lib.rs`) walks nested lists via `rustymath_buffer::walk`, rustymath's Python package's walker, with a collector that nests a level whose items differ in shape. Lists follow the shared import rule; dicts read as literals do. `rustymath_buffer::labels`: the one rule for dict keys and frame column labels, in both Python packages. A frame reads via `rustymath_buffer::frame` as a keyed vector of columns; `.df` turns it back. `None` as an item reads as NaN; a bare `None` doesn't convert → an operator given one returns `NotImplemented`.
- `syntax.py` wraps the native syntax tree with character spans and span-editing helpers.

`Array(existing)` makes an independent native handle. Assignment and `.keys`/`.names` setters replace the owner's handle, leaving prior views and captured functions unchanged. Both Python packages read written selectors as `structure::IndexPart` tokens via `rustymath/buffer/src/selection.rs` and plan them with `structure::plan_parts`, `⌷`'s structural planner; `structure::addressed_parts` routes source groups and expands `Rest` against the applicable frame. On a BPL array, Python's own kinds (`selection::native`: slices, keys, integers, lists of keys) decode in the buffer crate; Boolean masks select where true; other selectors become BPL values decoding as `⌷` decodes them (`Value::planned`). Pick paths select alone, as `⌷` reads them, keeping the written parts until the ending cell's geometry is known. `_Array.select`, `_Array.assign`: carrier-aware structural selection and writeback. Python assignment uses leading-axis broadcasting; language writeback keeps its own agreement.

Each `_Session` request waits for its evaluator mutex without the GIL, then evaluates on the caller's thread with the GIL released. A separate interrupt handle allows interruption from another thread; signal polling briefly takes the GIL. Python input and optional streaming-output callbacks cross at explicit boundary adapters. No Python numeric objects enter core values; arrays can drop on any thread without an unsafe Send implementation.

### Browser

`cargo wasm`: an incremental release-profile npm package with wasm-bindgen glue, language and input assets, grammar and canvas support. `--out DIR` leaves the docs' local playground assets alone; `--strip` removes function-name metadata for distribution. Keep wasm-bindgen glue and crate versions aligned through the workspace lock. Avoid fat LTO here: its rebuild cost and larger stack frames conflict with browser development and recursion limits.

Stack frames: Liftoff, V8's first compiler, gives each wasm local its own stack slot, used or not → a function that recursion passes through keeps its general path out of line, as Each, Rank and the outer product do (`each_items`), and `ErrorKind`, held by every frame's `Result`, stays 16 bytes in wasm32 (`transform::Stop`). In wasm, `Binder::reduce` and `Bindings::enter` stay out of line, keeping their locals out of the frames held at every recursion level. To find a frame that grew: read the function names in the stack of the overflow's `RangeError`, then compare those functions' wasm locals between builds; TurboFan frame size per function, in "stack slots": `node --no-liftoff --print-wasm-code-function-index=N`. `wasm-objdump -h DIR/basedpl_wasm_bg.wasm`: section sizes, `name` included. `twiggy diff` matches functions by full name, including crate hashes that change between builds → compare two builds' `twiggy top -n 1000000 -f json` listings with hashes removed.

Recursion limits: CI's two `wasm` jobs (`Test`, `Speed`) take Node's version from `.node-version`: TurboFan frame sizes vary between V8 versions enough to decide whether a recursion test overflows (one build's `each` shape: 0.68 MB for 171 levels under Node 24, 0.62 MB under Node 26). `tests/wasm.mjs` checks depth with Node's 192 KB reserve plus 80% of a Chrome worker's roughly 470 KB, 0.5575 MB in all → frames growing into the remaining 20% fail it. CI's x86-64 V8 takes more stack per level than Apple silicon's: `MAX_CALL_DEPTH` (`src/eval.rs`), the browser's depth limit, allows levels up to 1.48 times their Apple-silicon size. `basedpl.bpltests.wasm_stack(DIR)` measures each recursion shape's stack per level and below its first level, the figures the limit is set from; each trial runs in a fresh `node` process whose worker compiles the module, as the test's does (code compiled once and shared across workers gets different frames).

Browser `Session.run` streams MIME events and returns a protocol error or null. `eval` transfers values via `js.rs`, discards output, can't export BPL functions or operators; `bind` imports page values and functions. Typed arrays transfer without another page-worker copy. JavaScript functions live in a thread-local registry and core function nodes hold slots → values stay Send/Sync. `host_web.rs`: the browser's clock, synchronous I/O and fetch, RegExp behaviour. File and URL reads resolve against the configured base. Unsupported native filesystem and locale operations stay unavailable; browser `•nput` writes only stdout; `•js` is browser-only.

The playground and gallery load released assets from jsDelivr, or local `nbs/playground/` assets on localhost. Shared `bpl.js` owns editors, worker startup and output. The authored ES modules and font in `python/basedpl/browser/` need no evaluator: `browser/bpl-editor.js` exports grammar, configuration, editor options, font installation and explicit `install()`. Importing data never mounts the bar. Solveit, the playground and the gallery supply a normal-flow `#bpl-toolbar` slot; elsewhere the same component overlays the page without padding or height adjustment. One persisted collapse button keeps keyboard input active. `install()` reuses a connected controller; its `dispose()` closes it. Python magics call Solveit's `window.loadBplInput()` when present, else import the same public module from jsDelivr. Restarting a trapped or stopped worker loses its state. `worker.js`, `page.js` and `gallery.js` own their protocols and UI; `nbs/driver.js` documents canvas drawing data. Gallery demos: `.bpl` sources with shared preferences, checked natively by `language_examples`. Browser recursion tests cover both V8 compilers and fail with LIMIT before stack exhaustion.

## System functions and rendering

`system.rs` owns the system table: one `SystemFunction` per system function: case-insensitive name, call, valence, extension, result prototype, inverse. Its extension (`primitive::Extension`) is the field each primitive form holds too. A system function takes its right argument whole, or takes items (`primitive::Item`), mapping over a right argument holding several, with the left argument whole for each; one taking text also maps over each row of a character matrix, as `⍎` does.

- A function that acts asks the running levels where it acts (`Context::acts`), as output and input do: reading or writing files, network, clock or terminal, or making something new each call (`•index`, `•rand`). Others ask nothing; a batched run calls them once per cell.
- The parser resolves a known system name to its table entry (`system::Entry`) via `Builtin::find`, which also finds glyph primitives; `primitive::Builtin` holds either → a system name is a `NodeKind::Function` node, compiles to a constant and resolves to the function a process-wide table holds per builtin (`Builtin::function`), as a glyph does. An unknown system name stays a `NodeKind::System` node: VALUE error when evaluated.
- Code identifies a table function by its `SystemFunction`'s `Entry` (`Entry::PREFS`), never by name. A factory-made function (`•element "div"`) has no entry, though it shares its factory's name.
- Native records use ordinary function nodes and calls. Empty native item mapping returns its declared prototype without calling the function. `data::Options`: the shared keyed-option decoder; formats invent no option parsers of their own.

`optimize.rs`: `⇄` on `rustymath::optimize`; the left argument holds options. A method that can use a derivative (none named, L-BFGS, Levenberg–Marquardt, CG, MINRES) → one linearisation at the start (`derivative::linearized`) finds whether `∂` differentiates the function and gives its value there. `Goal` evaluates the function at points in the start's layout for `minimize`; under L-BFGS each value comes from a linearisation that `gradient` transposes at the same point (`linearized_at`) → one function run per value and gradient. With `"solve":$t`, `Residual` is the `Mapping` `solve` takes, or `solve_affine` with `"linear":$t` too. Where `∂` differentiates the function, `Residual` gives JVPs and vector–Jacobian products from one record per point, or the start's record for an affine function. A later point where `∂` gives UNSUPPORTED → `Residual::jvp` declines; rustymath takes forward differences for that Jacobian and later ones. A square linear system takes no transpose products → GMRES on A, not the normal equations. Option `precondition`'s function gives the preconditioner.

CSV columns, JSON arrays and Python lists share `data::imported`: a non-fill finite float, or any nonfinite float, promotes to float when every number converts losslessly; finite fills alone don't; otherwise items keep their kinds. JSON objects and Python dicts read as literals do (`keyed::vector`, `Value::from_parts`). Binary data: exact bytes. Writes validate before opening and create exclusively unless overwrite is explicit. Exports: `•csv⁻¹`, `•json⁻¹`, `•xml⁻¹`.

`regex.rs` shares host regex state between match and replace native functions; hosts keep their own regex syntax. `xml.rs`: keyed element trees; XML escaping and validation kept apart from HTML raw script/style and void-element rules. SVG has its own renderer. `image.rs` owns pictures, their options and animation timing, as plain pixel buffers; its `codec` module decodes and encodes via ImageIO on Apple targets (`image/imageio.rs`), the `image` and `png` crates elsewhere (`image/codecs.rs`). Native and browser renderers use the MIME and byte formats their frontends support. `plot.rs` stores specs and draws SVG on demand; the renderer owns defaults and validation. Rendering options are documented in their user pages and implementation comments.

`display.rs` owns plain, boxed and function display, elision and MIME rendering. Display settings affect implicit presentation, not returned values or `⍕`; explicit output prints all items. Display and source text read items, not storage: `Value::shown_dtype` (`array/text.rs`) gives the dtype compact storage of the items would take (`storage::items_dtype`'s items rule), read by the shared `ₓ` or width marker, plain display's choice between brackets and a strand, the bracketed grid plain display and `⍕` share (`display::table`, `display::bracketed`), a keyed table's corner and the boxed marker. `•mime` calls a renderer with echo off and cancellation active. Failed implicit rendering falls back to text; interrupts and timeouts propagate. `canvas.rs` serializes drawing data and typed bytes; `canvas.js` and `nbs/driver.js` own browser playback. Keep formatting, serialization and rich output separate contracts.

## Tests and reference data

`tests/core.rs`: public storage, layout and API behaviour, ownership, parser diagnostics and recovery. `equiv_in!` for session workflows, `fails_in` for errors; each expected expression runs in a fresh session after its code, under the settings the code leaves. `tests/core.rs` never changes settings: they're one process-wide store → checks that change them live in `tests/settings.rs`, run in turn in one test, each from the defaults. Both binaries share `tests/common/mod.rs`. Keep constructors for representation, prototype and buffer checks. Self-contained language cases: `tests/reference/core.bpl`. `cli/tests/cli.rs` and Python's pseudo-terminal tests exercise the installed process and editor boundary.

`reference.rs` serves Rust tests and worker requests.

- Every reference case gets a fresh session; documentation examples share one per BPL code block, starting from default settings. Each page starts with no kept plans or compiled kernels, as a new process does (`program::forget_plans`, `jit::forget_kernels`) → an example showing block counts or compiling gives the same output alone (`check_page`) or after other pages (`language_examples`).
- A reference file's leading `•prefs` line sets all its cases' settings. Optional `⍝⍝ setup`: shared definitions, initialized separately for each run and its expectation. A section's inline `•prefs` suffix runs before setup.
- Each case runs five times, each from the defaults and the file's header: `batch` off; on; on with fusion's small sizes, every block stage compiling its parts; the same with no compiled parts, only where the previous run used one (`blocks::compiled_runs`); on, with its code as a dfn body one session calls twice (`twice`), checking that the second call, which runs the statements the first recorded, gives the first's value, storage kind, error and output (skipped for code that can't be a dfn body). Header flags drop runs: `batched` the `batch`-off run; `unfused` the small-size runs; `compiled` the no-compiled-parts run, for a case whose value says whether a stage compiled.
- Every run checks each program before it runs (`program::verify`): each step reads values before its own; each read lays out as many items as its node holds; each node's description is what the shared planners give its step on its operands. A breach panics with the program's listing.
- `tests/reference.rs` checks cases in a child process of itself per core, Python's `check_file` in a worker per core: a process evaluates one case at a time.
- Each expectation evaluates after its code, under the settings the code leaves. A float matches within 1e-13, or 8 ulps of its own width where greater, unless the header sets a tolerance (`reference::same_atom`). `.bpl` files define active coverage. Captured foreign expectations have no exactness; local expectations compare exactness and structural values independently, and fix where storage is mixed: the result must be mixed exactly where the expectation is, at each nesting level (`kind_difference`), unless the header carries `mixed`.
- Pending gaps go in inventory JSONL, not passing error tests. Format and review/activation workflow: `tests/reference/README.md`. `python/basedpl/reference.py`, `bpltests.py` and `scripts/reference.py` own import, capture, inventory and worker checks. `lib/*.bpl`: readable dfn examples; modules import other library files with private relative names.

`tests/scaling.rs`: time and allocation growth, result-size allocation budgets. `tests/speed.rs` reads native and browser budgets from `speed/*.bpl` via `timing.rs`; the worker and Python measurement tools reuse it. Both, and `tests/reference.rs`'s children, register rustymath's memory guard and turn on its checks (`memory::set_checks`) in one-case-at-a-time processes: a reference case leaving more bytes held in large allocations than it found, on each of two runs, fails as a leak, as does a speed case whose timed runs leave more than its first run. A free or reallocation passing more bytes than its block holds aborts with a backtrace. `tests/units.rs` reads existing incremental object files, checking unit size without building. Python tests cover conversion, cancellation and frontend behaviour, not a second Rust semantic suite. Combine related checks into readable tests.

Before each release, run `bpl-tests prerelease` from basedpl's root, in a shell, not a kernel, while no one else edits either repository. It runs both repositories' release checks and saves:

1. Builds, tests and saves, in parallel, each step starting once the steps whose output it reads pass: in each repository `cargo develop`, `cargo test`, `pytest -q`, `nbdev-prepare`, and `cargo test --profile checked` in its own target directory; also basedpl's `cargo test --test routes`. basedpl's development build includes editor generation; its Node tests, notebooks and `target_builds` wait for that data; browser tests follow `target_builds`.
2. Timings, one at a time, nothing else running: `cargo test --test speed` in each repository with `<NAME>_COSTS` set, rustymath's Python speed test, `thread_scaling`, the browser speed test.
3. `nbdev-clean` in both repositories, even after a failure.

The first failure ends the run unless `--keep-going`. Summary: each step's status, time and log. `--dry-run` lists the steps in order without running them. It stops before starting if `node_modules` or the Node version `.node-version` names is missing, and notes when basedpl needs an unreleased rustymath version (rustymath then ships first). It never commits, pushes or tags.

`cargo test --profile checked`: the test profile with debug assertions on, adding `session()`'s turn check and the standard library's checks in unsafe code. They cost 12-55% per call, too much for the test profile the budgets measure; the speed and scaling tests mark themselves ignored under debug assertions → that run checks correctness only.

Confirm the clean tree and `[workspace.package].version`, then run `ship-release` without flags. Python gets that version via `dynamic = ["version"]`. Fastship pushes and tags the current version, leaves publication to the `Release` workflow, and bumps Cargo without rebuilding. No changelog step. Never commit, push, tag or publish without approval.
